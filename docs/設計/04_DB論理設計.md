本書は、`01_要件定義.md` と `03_技術選定.md` にもとづき、データベースの論理設計を定義する文書です。

- 文書状態: 初版

## 2. 共通の設計方針

### 2.1 命名規約

| 対象 | 規約 | 例 |
| --- | --- | --- |
| テーブル名 | snake_case・複数形 | `projects`, `team_trainees` |
| カラム名 | snake_case | `corporate_number` |
| 主キー | `id` | |
| 外部キー | `<単数形テーブル名>_id` | `company_id` |
| 真偽値 | `is_` で始める | `is_active` |
| 日時 | `_at` で終える | `created_at` |

### 2.2 データ型の方針

| 用途 | 型 | 補足 |
| --- | --- | --- |
| 主キー | `BIGINT UNSIGNED AUTO_INCREMENT` | マスタ系はコード文字列を主キーとする |
| 日時 | `DATETIME` | **UTCで保存**し、アプリケーション側でJSTへ変換する。`TIMESTAMP` は2038年問題とセッションタイムゾーン依存があるため使用しない |
| 日付 | `DATE` | 講義日、休業日 |
| 時刻 | `TIME` | 講義の開始・終了時刻 |
| 区分値 | `VARCHAR(32)` + `CHECK` 制約 | `ENUM` は値の追加が `ALTER TABLE` を伴うため使用しない。定数はアプリケーション側と `CHECK` の二重で管理する |
| 金額 | `BIGINT` | 円単位の整数 |
| 所要時間 | `DECIMAL(3,1)` | 0.5時間単位（5.7） |
| ファイルサイズ | `BIGINT` | バイト単位。上限52,428,800（50MB） |

### 2.3 共通カラム（作成・更新情報）

要件5.17にもとづき、業務データを保持するテーブルには次の4カラムを持たせます。履歴は追加せず、最新の値のみを保持します。

| カラム | 型 | NULL | 説明 |
| --- | --- | --- | --- |
| `created_at` | DATETIME | 不可 | 作成日時 |
| `created_by` | BIGINT UNSIGNED | 可 | 作成者。`users.id` を参照 |
| `updated_at` | DATETIME | 不可 | 最終更新日時 |
| `updated_by` | BIGINT UNSIGNED | 可 | 最終更新者。`users.id` を参照 |

- **`created_by` / `updated_by` が NULL の場合は「システム」による操作を意味します**（5.17）
- アカウント完全削除時は `ON DELETE SET NULL` とし、値を NULL にします。この場合も「システム」と表示されるため、表示名を残す必要がある箇所は次項の方針に従います
- マスタ系・スナップショット系など更新者の記録が不要なテーブルは、`created_at` / `updated_at` のみを持ちます（各テーブル定義に明記）

### 2.4 削除の方針

要件では論理削除を使わず、**すべて物理削除**とします（5.3, 5.4, 5.6, 5.15）。これに伴い次のルールを定めます。

**(1) 削除履歴は別テーブルに残す**

会社・アカウント・申請案件の削除は、`deletion_logs` に記録します。本体データは物理削除されるため、履歴側に必要な値を複製して保持します。

**(2) 利用者名は削除後も残す**

要件5.4に「アカウントを完全削除しても、過去の申請案件、掲示板投稿、予約などに表示される利用者名は残す」とあります。そのため次のルールを適用します。

> 利用者名を画面に表示し、かつアカウント削除後も表示を維持する必要がある箇所は、`user_id`（`ON DELETE SET NULL`）と**表示名のスナップショット列**を併せて持つ。

該当箇所は `projects.primary_staff_name`、`board_posts.author_name`、`reservations.requested_by_name` / `instructor_name`、`deletion_logs.deleted_by_name` です。

**(3) 受講者名は削除後に残さない**

要件5.6に「受講者を削除した場合は、研修完了後の過去記録にも受講者の名前を残さない」とあります。**アカウントとは逆の方針**です。受講者を参照するテーブル（`team_trainees`、`attendance_records`、`employment_contracts`）はすべて `ON DELETE CASCADE` とし、スナップショットは持ちません。

### 2.5 一意制約と検索

- 照合順序は `utf8mb4_ja_0900_as_cs` で統一します。ログインIDの大文字小文字は区別されます（要件5.4、技術選定書4.2）
- 一覧画面の検索は `LIKE` による部分一致とし、検索対象列にインデックスを付与します（前方一致のみ有効）
- 各一覧は50件ページングです（5.3, 5.4, 5.14）

## 5. 主要な設計判断

### 5.1 マスタの複製（スナップショット）

チームにコースを紐づけた時点で内容を複製し、以後マスタが変更されても複製内容は変わりません（5.7）。

- **複製する**: コース内容（`team_courses`）、講義コマ（`team_course_sessions`）、日別コマ割当（`team_pattern_days`）
- **複製しない**: 研修プログラム名、職種カテゴリ名 — コードで参照し、常にマスタの最新名称を表示します
- マスタは参照されている限り削除できず、無効化のみ可能です。無効化されたマスタを参照する既存チームの表示は維持されます

この設計により、マスタを改訂しても過去のチームの記録が変化しません。

### 5.2 削除時の名前の扱い

要件には**方向の異なる2つのルール**があり、設計上の対応も分かれます。

| 対象 | 要件 | 設計 |
| --- | --- | --- |
| アカウント | 削除しても過去の記録に表示される利用者名は残す（5.4） | `user_id` を `SET NULL` にし、**表示名のスナップショット列を併設** |
| 受講者 | 削除したら研修完了後の過去記録にも名前を残さない（5.6） | 参照テーブルをすべて `CASCADE` で削除。スナップショットは**持たない** |

### 5.3 一意制約でDB側に担保させたルール

アプリケーションの実装漏れがあってもデータが壊れないよう、次のルールはDB制約で担保します。

| ルール | 制約 | 参照 |
| --- | --- | --- |
| ログインIDはシステム全体で重複不可 | `users.login_id` 一意 | 5.4 |
| 同じ法人番号の会社を重複登録できない | `companies.corporate_number` 一意 | 5.3 |
| 同じ会社内で雇用保険被保険者番号の重複不可 | (`company_id`, `insurance_number`) 一意 | 5.6 |
| 同じ申請案件内で受講者をチームに重複登録できない | `team_trainees` の (`project_id`, `trainee_id`) 一意 | 5.6 |
| 1種類の必要書類につきファイルは1つ | (`project_id`, `document_type`) 一意 | 5.2 |
| 受講者1人につき雇用契約書は1ファイル | `employment_contracts.trainee_id` 一意 | 5.2 |
| 1予約枠に対してチームは1つ | `teams.reservation_id` 一意 | 5.5 |
| 1申請案件に契約書・見積・請求書は各1件 | 各テーブルの `project_id` 一意 | 5.8〜5.10 |

### 5.4 アプリケーション側で検証するルール

DB制約では表現できないため、アプリケーション側（認可付きのデータ操作関数）で検証します。

- ステータスは決められた順序で進め、前に戻さず、途中を飛ばさない（5.1）
- 全書類および全受講者の雇用契約書が承認済みでなければ「書類収集完了」へ進めない（5.2）
- 会社の必須項目がすべて入力され、受講者が1人以上いなければ「契約書送付」へ進めない（5.3）
- 同一日時の予約枠数の上限は「有効な講師数 − 1」（5.5）
- 1人の講師に同じ日時の講義を重複して割り当てない（5.5）
- 有効なシステム管理者が1人だけの場合、そのアカウントを無効化・削除・権限解除できない（5.4）
- 未完了案件の主担当になっている事務員アカウントを無効化・削除・権限解除できない（5.4, 5.16）
- 今後の確定済み予約を担当している講師アカウントを削除・権限解除できない（5.4）

### 5.5 認可とデータアクセス

技術選定書4.5の方針に従い、認可はデータ取得関数に埋め込みます。特に代理店のスコープはDB構造上の経路が長いため、必ず共通の関数を経由させます。

```
代理店アカウント → users.agency_id
                 → companies.referral_agency_id が一致する会社
                 → その会社の projects
```

代理店は閲覧のみで、登録・編集・削除・投稿・通知の対象外です（5.24）。

## 6. インデックス方針

一覧画面の要件（5.3, 5.4, 5.14）にもとづき、次の方針とします。

- 検索対象列（会社名、利用者名、ログインID、案件番号、案件名）に単独インデックスを付与します
- 絞り込み条件（ステータス、権限、有効／無効、主担当）に単独インデックスを付与します
- 初期表示順（作成日時の降順、案件番号の降順）に対応するインデックスを付与します
- 部分一致検索（`LIKE '%...%'`）はインデックスが効きませんが、最大10,000社・50,000案件の規模では性能要件（5.22）を満たします。不足した場合はInnoDBの全文検索インデックス（ngramパーサ）へ移行します
