## 4. アプリケーション層の選定理由

### 4.1 Next.js（App Router）による一体型構成

本システムの複雑度は画面表現ではなく、**認可と業務ルール**（ステータス遷移、雇用契約書の会社単位承認、マスタのスナップショット複製）に集中しています。

サーバーコンポーネントを用いると、データ取得と認可を同一のサーバー関数に閉じ込められます。

```tsx
// app/projects/page.tsx  ← サーバー上でのみ実行される
export default async function ProjectsPage() {
  const user = await getSession()
  const projects = await findProjectsForUser(user)  // 認可をここに集約
  return <ProjectTable rows={projects} />
}
```

ブラウザから直接呼べるAPIが存在しないため、代理店が他社の案件を取得する経路がそもそも発生しません。API仕様書の管理と、フロント・バックエンドで認可を二重実装する工数も不要になります。

要件5.18で専用スマートフォンアプリを作成しない方針が確定しているため、API分離の主な利点である「複数クライアントからの再利用」は本件では発生しません。

**採用にあたっての注意点**

- サーバーコンポーネントとクライアントコンポーネントの境界設計に習熟が必要です
- **Server Action は実質的に公開エンドポイントです。** すべてのServer Actionの先頭で権限検証を行う規約を設け、レビュー項目に含めます
- Next.js はバージョン更新が速いため、メジャーバージョンを固定し、更新時期を計画的に設けます

予約カレンダー、カリキュラム編集、掲示板など操作が複雑な画面は、その画面のみクライアントコンポーネントとして構築します。

### 4.2 MySQL

データベースは MySQL 8.4 (LTS) を採用します。運用実績と社内での扱いやすさを優先した判断です。

本要件に対して MySQL 8 で不足する機能はありません。当初 PostgreSQL の利点として挙げていた項目は、いずれも次のとおり解消されます。

| 論点 | MySQL 8 での扱い |
| --- | --- |
| 「同じ会社内では雇用保険被保険者番号を重複登録できない」（5.6） | `(会社ID, 雇用保険被保険者番号)` の複合ユニークキーで担保できます。要件では受講者・会社・アカウントをいずれも**完全削除**する方針（5.3, 5.4, 5.6）のため、論理削除を考慮した条件付き一意制約は必要ありません |
| 従業員数0以上、資本金0円以上などの値制約（5.3） | MySQL 8.0.16 以降の CHECK 制約で担保できます |
| チームへ複製するマスタのスナップショット（5.7） | ネイティブの JSON 型で保持できます。スナップショットは検索対象ではないため、インデックスは不要です |
| 会社名・利用者名・案件名の検索（5.3, 5.4, 5.14） | 最大10,000社・50,000案件の規模では `LIKE` による部分一致で性能要件（5.22）を満たします。将来的に不足した場合は、InnoDB の全文検索インデックス（ngram パーサ）へ移行できます |

規模が最大50,000案件・同時30人であるため、Aurora は過剰です。RDS の汎用インスタンスで十分に要件を満たします。

#### 文字コードと照合順序

インスタンス作成後の変更が容易ではないため、設計段階で確定させます。

- 文字コードは `utf8mb4` とします
- MySQL 8 の既定の照合順序 `utf8mb4_0900_ai_ci` は**アクセント非依存**のため、日本語では濁点・半濁点を区別しません（「ハ」「バ」「パ」が同一と判定されます）。会社名や受講者氏名の検索・重複判定で誤動作するため、**採用しません**
- 照合順序は `utf8mb4_ja_0900_as_cs`（アクセント区別・大文字小文字区別）で統一します

**ログインIDの大文字小文字は区別します。** `Tanaka` と `tanaka` は別のログインIDとして登録でき、ログイン時も入力どおりに一致判定します。この方針により、列ごとに照合順序を分ける必要はなく、全テーブル・全列で `utf8mb4_ja_0900_as_cs` を使用します。

### 4.3 Drizzle ORM

スキーマを TypeScript で定義し、SQL に近い記述でクエリを構築する ORM です。マイグレーションは `drizzle-kit` で管理します。本要件には、ORM 選定に強く効く特徴が3つあり、いずれも Drizzle が有利です。

| 本要件の特徴 | Drizzle での扱い |
| --- | --- |
| **一覧画面の検索条件・並び替え列が可変**（5.3, 5.4, 5.14） | `$dynamic()` により、条件分岐を含むクエリを段階的に組み立てられます。会社一覧・アカウント一覧・案件一覧の3画面すべてに現れるため、記述量の差が積み上がります |
| **CSVによるマスタの一括登録・更新**（5.7） | MySQL の `INSERT ... ON DUPLICATE KEY UPDATE` を `onDuplicateKeyUpdate()` で直接利用できます。コース132件・講義コマ約1,700件の取込を1文で処理できます |
| **認可をデータ取得関数に埋め込む**（4.5） | 代理店スコープなどの認可条件をクエリ断片として関数化し、合成して使えます |

補助的な利点として、コード生成のステップがなく、生成物とスキーマの同期ずれが起きません。

**採用にあたっての注意点**

- マイグレーション運用の成熟度は Prisma に劣ります。生成された SQL を必ずレビューし、破壊的変更（列の削除・型変更）は手を入れる前提で運用します
- スキーマ定義が TypeScript のため、テーブル数が増えたときの見通しが悪くなりがちです。ドメイン単位でファイルを分割する規約を設けます
- GUI が必要な場合は Drizzle Studio を使用します

**代替案**として Prisma があります。マイグレーション運用の成熟度と情報量では明確に上であり、チームが ORM に不慣れな場合はこちらが安全です。ただし MySQL では一括 upsert がネイティブに扱えず、CSV取込で1行ずつの upsert または生SQLへの迂回が必要になります。

### 4.4 認証・セッション（自前実装）

**Amazon Cognito は採用しません。** 要件との不適合が複数あります。

| 要件 | Cognito での課題 |
| --- | --- |
| ログインIDにメールアドレスを使用しない（5.4） | ユーザー名運用は可能だが、標準機能の多くがメール前提で設計されている |
| 管理者が仮パスワードを再生成し、メール・LINEで個別に伝える（5.4） | Cognito のパスワードリセットフローと運用が合わず、大幅なカスタマイズが必要 |
| パスワード変更・アカウント無効化で全端末を即時ログアウト（5.19） | トークンの即時失効に追加実装が必要 |
| 権限変更を即時反映（5.19） | トークンに権限を含めると即時反映できない |

これらを回避するカスタマイズ量が、自前実装の工数を上回ります。またログイン画面のレート制限は WAF 側で行う方針（5.20）のため、Cognito の防御機能を使う必然性もありません。

**Auth.js (NextAuth) も採用しません。** ID・パスワード認証（Credentials Provider）とデータベースセッション戦略を併用できない制約があり、要件の「全端末の即時ログアウト」「権限の即時反映」を素直に実装できないためです。

**採用する実装方式**

- パスワードハッシュ: **Argon2id**（`@node-rs/argon2`）
- セッショントークン: 暗号論的乱数32バイトを生成し、Cookie（`httpOnly` / `Secure` / `SameSite=Lax`）で保持する
- データベースには**トークンのハッシュ値を保存**し、平文は保存しない
- セッションテーブル: `id` / `user_id` / `token_hash` / `expires_at` / `created_at` / `last_used_at`
- 有効期限は発行時点から30日（5.19）
- 全端末ログアウト = 該当 `user_id` のセッション行を削除する
- **権限はセッションに含めず、リクエストごとにデータベースから読む** — これにより権限変更が即時反映される（5.19）

同時利用30人という規模のため、リクエストごとのセッション照会による負荷は問題になりません。

### 4.5 認可の実装方針

認可はライブラリを導入せず、次の規約で実装します。アクターが6種類に固定されており、汎用的な権限エンジンは不要なためです。

- **データ取得関数に認可を埋め込む。** `findProjectsForUser(user)` のように、利用者を引数に取らないデータ取得関数を作らない
- 代理店のスコープ（自社が紹介代理店に設定されている会社のみ）は、この関数内で必ず適用する
- 1アカウントの複数権限は、`user_roles` テーブルによる多対多で表現する
- すべての Server Action の先頭で `requireRole()` による検証を行う
- 認可の境界はユニットテストで網羅する

### 4.6 ファイル保管（S3 + 署名付きURL）

1ファイル最大50MB（5.2）は、Next.js の Server Action の標準ボディ上限を大きく超えます。アプリケーションサーバーを経由させず、次の経路とします。

1. サーバーが権限を検証し、S3への署名付きPUT URLを発行する
2. ブラウザが S3 へ直接アップロードする
3. 完了後、サーバーにファイルキーを登録する

- バケットは非公開とし、ダウンロードも署名付きGET URLで行います
- 差し替え時は前のファイルを削除します（履歴を保持しない方針・5.2）
- アップロードの進捗表示は行わない方針（5.22）のため、実装は単純になります

### 4.7 PDF生成（Puppeteer）

見積もり兼発注書・請求書（5.9, 5.10）を生成します。**Puppeteer で HTML/CSS をPDF化する方式**を採用します。

- 帳票レイアウトをHTML/CSSで記述できるため、レイアウト調整の反復コストが最も低くなります
- 日本語フォント（Noto Sans JP等）をコンテナイメージに同梱します
- コンテナイメージが約300MB増加しますが、Fargate では許容範囲です

帳票は**現行システムの見積もり兼発注書・請求書を踏襲する**方針です。既存の見た目を再現する作業になるため、罫線・表組み・押印位置をHTML/CSSで直接調整できる利点がそのまま効きます。

代替案の **@react-pdf/renderer** はイメージが軽量ですが、独自のレイアウトエンジンのため既存帳票の再現に手間がかかります。本方針のもとでは採用しません。

なお、この選択は Lambda を採用しなかった理由のひとつでもあります。

### 4.8 メール送信（Amazon SES）

- 見積もり兼発注書・請求書をPDF添付で送付します（5.9, 5.10）
- 本番運用前に**サンドボックス解除の申請**が必要です（リードタイムを計画に含めます）
- 送信ドメインに SPF / DKIM / DMARC を設定します
- バウンス・苦情の通知を受け取り、記録します
- 契約書の署名依頼メールは FREE SIGN 側から送信するため、本システムからは送信しません（5.8）

### 4.9 システム内通知

通知テーブルへの登録と、クライアント側からの定期ポーリング（30〜60秒間隔）で実装します。同時利用30人・通知はベルアイコンの未読件数のみ（5.13）という要件に対し、WebSocket や SSE を導入する必要はありません。

### 4.10 その他

- **お知らせのリッチテキスト（5.23）**: Tiptap を使用し、太字・斜体・下線・文字色・文字サイズ・リンクのみに機能を限定します。保存内容は表示前に必ずサニタイズし、XSS を防ぎます
- **CSV一括取込（5.7）**: papaparse で解析します。文字コードは `encoding-japanese` で自動判定し、UTF-8（BOM有無を問わない）と Shift_JIS の両方を受け付けます。事務員が Excel で編集して再アップロードした場合、Windows 版 Excel は既定で Shift_JIS に変換して保存するため、両対応は必須です。BOM は除去したうえで解析します
  - `docs/data/` の初期データ6ファイルは UTF-8（BOM付き）であることを確認済みです
  - `courses.csv` の「目的」列など、値に改行を含むフィールドがあります。行単位の分割ではなく、必ずCSVパーサで解析します
- **郵便番号→住所の自動入力（5.3）**: 日本郵便が公開する郵便番号データを自前のテーブルに取り込み、月次バッチで更新します。外部APIに依存せず、応答時間と可用性を自システムで制御できます

## 5. インフラ構成

### 5.1 全体構成

```
Route 53
  └─ ALB (HTTPS / ACM証明書)        ← AWS WAF をアタッチ
       └─ ECS Fargate (Next.js)
            ├─ RDS MySQL
            ├─ S3 : アップロードファイル
            └─ SES

AWS Backup ─┬─ RDS      → Backup Vault (Vault Lock)
            └─ S3       → Backup Vault (Vault Lock)

Secrets Manager : DB認証情報 / FREE SIGN APIキー
CloudWatch Logs / アラーム : ログと監視（SNS経由で開発チームへ通知）
EventBridge Scheduler : 郵便番号データの月次更新 / ステージング環境の起動・停止
```

CloudFront は初期構成に含めません。同時30人という規模では ALB からの直接配信で性能要件（5.22）を満たせるため、構成要素を減らすことを優先します。

### 5.2 主要リソースの初期構成

| リソース | 初期設定 | 備考 |
| --- | --- | --- |
| ECS Fargate | 0.5 vCPU / 1GB × 2タスク | 冗長化のため2タスク。負荷を見て調整 |
| RDS | db.t4g.small / gp3 20GB | 拡張はストレージ自動スケーリングで対応 |
| RDS 冗長化 | **Single-AZ**（確定） | 要件にHA要求はなし。運用開始後に停止の影響が大きいと判断した時点で Multi-AZ へ変更する |
| S3 | バージョニング有効 | 誤削除への一次的な備え |

### 5.3 バックアップ設計

要件5.20の各項目に対し、**AWS Backup** で対応します。RDS と S3 を単一の仕組みで管理でき、要件をそのまま設定に写像できるためです。

| 要件（5.20） | 対応 |
| --- | --- |
| DBとアップロードファイルを1日1回自動でバックアップ | AWS Backup のバックアッププランで日次実行 |
| 保存期間は30日 | ライフサイクル設定で30日保持 |
| 本番と同じAWSアカウント内の専用の保管先 | 同一アカウント内に専用の Backup Vault を作成 |
| 本番のDB・ファイル保存先とは別に用意 | Vault は本番リソースから独立 |
| 削除保護を設定し、保存期間中は削除できない | **Vault Lock** を有効化 |
| バックアップへのアクセス権限を本番実行権限と分ける | Vault のリソースベースポリシーで、アプリケーション実行ロールから削除権限を除外 |
| 別AWSアカウント・別リージョンへの複製は行わない | コピー設定を行わない |

### 5.4 不正アクセス対策

要件5.20にもとづき、**AWS WAF のレートベースルール**をログイン画面に適用します。

- 対象を `/login` のパスに限定します（スコープダウンステートメント）
- 送信元IPアドレス単位で評価します
- **しきい値は 100リクエスト / 5分 / IP** とします
- アカウントの無効化・ロックは伴いません（要件どおり）

しきい値の根拠は次のとおりです。システム全体の同時利用が30人（5.21）であるため、正当な利用でログイン画面へ大量のリクエストが飛ぶ状況は発生しません。一方でクライアント企業のオフィスは NAT により複数人が同じグローバルIPを共有するため、厳しすぎる設定は始業時の一斉ログインで正当な利用者を巻き込みます。100回/5分は、正当な利用では到達せず、ブルートフォースを1時間あたり1,200回に抑える水準です。

導入は段階的に行います。

1. まず**カウントモード**で1〜2週間運用し、CloudWatch で実際のリクエスト数を観測する
2. 誤検知がないことを確認したうえで、ブロックを有効化する
3. 運用開始後も実データに基づいてしきい値を見直す

**アップロードファイルのウイルススキャン**

導入しません。要件に定めがなく、費用とスコープの判断として見送りました。

受け入れるリスクを明記します。本システムは、社外のクライアントと代理店がアップロードしたファイルを、社内の事務員・社労士がダウンロードして開く構造です（5.2, 5.9, 5.12）。感染したファイルが混入した場合、社内端末が感染する経路になります。この対策は利用者端末側のウイルス対策ソフトに委ねる前提とします。

運用開始後に必要と判断した場合は、GuardDuty Malware Protection for S3 を追加できます。その際はアプリケーション側に「スキャン完了までダウンロードさせない」状態管理の追加が必要です。

### 5.5 環境

**本番環境**と**ステージング環境**の2環境を構築します。インフラは Terraform で管理し、環境差分を変数で吸収します。

ステージング環境を設ける理由は、次の2つが本番以外では検証できないためです。

- **FREE SIGN の Webhook 受信**（6.1）— 外部から到達可能なURLが必要で、ローカル環境では検証できません
- **SESのメール到達性**（4.8）— DKIM署名や迷惑メール判定は、実際にDNSを設定して送信しなければ確認できません

この2つは本システムの中核機能であるため、本番で初めて動かす事態を避けます。

**ステージングは業務時間のみ稼働させます。**

- 構成は縮小版とします（Fargate 1タスク、RDS 最小インスタンス）
- 夜間・休日は ECS のタスク数を0にし、RDS インスタンスを停止します
- 起動・停止は EventBridge Scheduler で自動化します
- 投入するデータは、カリキュラムマスタのCSVと検証用のダミーデータとします。データ移行を行わない方針（1.1）のため、本番データの複製は発生しません

### 5.6 CI/CD

1. GitHub Actions でテスト・型検査・Lint を実行する
2. コンテナイメージをビルドし、ECR へ push する
3. データベースマイグレーションを ECS の単発タスクとして実行する
4. ECS サービスをローリング更新する

### 5.7 監視・アラート

要件5.23は「重大な障害を検知してもシステム管理者へメール通知を送らない」と定めています。これはシステム利用者に対する仕様であり、開発・運用チームが異常を検知する仕組みとは別のものです。**顧客側のシステム管理者には通知せず、開発チームのみが検知する構成**とします。

CloudWatch アラームから SNS 経由で通知します。Sentry などの外部サービスは導入しません。

監視対象は次のとおりです。いずれも利用者側にエラーが表示されないまま放置されやすい障害であることを基準に選定しています。

| 監視対象 | 検知できない場合に起きること |
| --- | --- |
| FREE SIGN の Webhook 受信処理の失敗 | 締結済みPDFが取得されないまま放置される（6.1） |
| SES の送信失敗・バウンス率 | 見積もり兼発注書・請求書がクライアントに届いていない（5.9, 5.10） |
| 郵便番号データ月次更新バッチの失敗 | 住所の自動入力が古いデータのまま動き続ける（4.10） |
| ECS タスクの異常終了・再起動の頻発 | 断続的なエラーに気づけない |
| RDS のディスク空き容量・CPU使用率 | 逼迫してから障害として顕在化する |
| ALB の 5xx エラー率 | アプリケーション障害の早期検知 |

通知先（開発チームの共有メールアドレス、または Slack の Incoming Webhook）は構築時に設定します。

### 5.8 ドメインとSSL証明書

本システム専用のドメインを**新規取得し、Route 53 でホストゾーンを管理**します。

- SSL証明書は ACM で発行し、DNS認証（CNAMEレコード）で検証します。ホストゾーンが同一アカウント内にあるため、検証と自動更新に手作業が発生しません
- SESの送信元ドメインにも同じドメインを使用し、SPF / DKIM / DMARC のレコードを Route 53 に設定します（4.8）

外部組織との調整が不要なため、DNS 起因のリードタイムは発生しません。残るリードタイムは **SES のサンドボックス解除申請**のみです。解除前は検証済みアドレスにしか送信できず、クライアント宛の送信テストが行えないため、構築の早い段階で申請します。

## 6. 外部連携

### 6.1 FREE SIGN（電子契約）

要件5.8の「FREE SIGN」は、**freeeサイン（旧 NINJA SIGN）**を指すものとして調査しました。公開されている OpenAPI 定義（`https://ninja-sign.com/v1/openapi.yaml`）と Webhook 仕様（`https://ninja-sign.com/webhook/doc`）にもとづき、要件5.8の各項目に対する実現可否を確認しています。

#### 認証方式

`POST /v1/token` に `client_id` と `client_secret` を送り、アクセストークンを取得します。利用者のログインを介さないサーバー間連携が可能です。

- アクセストークンには有効期限があるため、トークンをキャッシュし、失効時に再取得する処理を実装します
- `client_id` / `client_secret` は Secrets Manager で管理します

#### 要件5.8とAPIの対応

| 要件（5.8） | 対応するAPI | 可否 |
| --- | --- | --- |
| 事務員の送付操作でFREE SIGNから署名依頼を送信する | `POST /v1/pdf_documents`（文書アップロード）→ `POST /v1/documents/{id}/confirmations`（文書送信） | 可 |
| 署名依頼メールの再送 | `POST /v1/documents/{id}/re_confirmations`（文書再送信） | 可 |
| 送付の取り消しと、FREE SIGN側の署名依頼の無効化 | `PUT /v1/documents/{id}/signature_requests/cancel`（文書承認依頼キャンセル） | 可（意味の範囲は要確認） |
| 締結完了の検知 | Webhook `document_status_changed`。文書ステータスが `concluded`（完了）になったことで判定する | 可 |
| 締結済みPDFの自動取得と保存 | `GET /v1/documents/{id}` | 可（下記の手順が必要） |

文書ステータスは `draft`（作成中）/ `in_progress`（確認待ち）/ `awaiting_receipt`（受け取り待ち）/ `approved`（要確認）/ `concluded`（完了）/ `rejected`（却下）/ `expired`（有効期限切れ）/ `trashed`（削除済み）の8種類です。

#### 締結済みPDFの取得手順

単純な1回のダウンロードではなく、2段階の手順とリトライが必要です。

1. `GET /v1/documents/{id}` を `Accept: application/json` で呼び、`timestamped` が `true` であることを確認する
2. 同じエンドポイントを `Accept: application/pdf` で呼び、PDFを取得する
3. PDFの生成処理中はエラーが返るため、**時間を置いて再実行する**（API仕様に明記されています）

このためPDF取得は同期処理にせず、リトライを伴う非同期の取得処理として実装します。

#### Webhookの信頼性（設計上の重要事項）

Webhook 仕様に「ネットワークエラー等により届かなかったり、複数回届いたりする場合がある」と明記されています。**配信は保証されません。** したがって次の2点を必須とします。

- **冪等性の確保**: 同じ文書・同じステータスの通知を複数回受け取っても、処理結果が変わらないようにする
- **ポーリングによる補完**: Webhook のみに依存せず、送付済みで未締結の契約書を定期的に `GET /v1/documents/{id}` で確認する処理を併設する

署名検証は、`X-NinjaSign-Signature` ヘッダー（`sha256=<ハッシュ値>` 形式）を、事前に設定したシークレットを用いた HMAC-SHA256 で検証します。

#### 判明した制約

- **アップロードするPDFは10MB以下**です。要件5.2のファイル上限50MBとは別の制約であり、契約書の元ファイル作成時に考慮が必要です
- レート制限はAPI仕様に記載がありません。ベンダーへの確認事項とします

#### ベンダーへの確認事項

公開情報では確定できず、freee社への確認が必要な項目です。

1. Web API の利用に必要な契約プラン（無料プランやスタータープランで利用可能か）
2. Webhook URL の登録方法と、登録できるURL数
3. 「文書承認依頼キャンセル」が、送信済みの署名依頼の無効化を含むか（要件5.8の「送付を取り消すと、FREE SIGN側の署名依頼も無効にする」を満たすか）
4. APIのレート制限
5. テスト環境（サンドボックス）の提供有無

## 7. 見送った選択肢

| 選択肢 | 見送った理由 |
| --- | --- |
| Amazon Cognito | ログインID・仮パスワード運用・即時失効・即時権限反映のいずれも要件と不適合（4.4） |
| Auth.js (NextAuth) | ID/パスワード認証とDBセッション戦略を併用できず、即時失効を実装しにくい（4.4） |
| SPA + API 分離構成 | 認可を二重実装することになる。専用アプリを作らない方針のため、API公開の利点が発生しない（4.1） |
| Lambda + API Gateway | 50MBアップロード、Puppeteer同梱、コールドスタートのいずれも本要件では不利 |
| PostgreSQL | 条件付き一意制約などの利点はあるが、要件が完全削除方針のため本件では効かない。運用実績を優先し MySQL を採用（4.2） |
| Aurora / Aurora Serverless | 最大50,000案件・同時30人の規模に対して過剰。RDSで十分 |
| WebSocket / SSE による通知 | 通知はベルアイコンの未読表示のみ。ポーリングで要件を満たす（4.9） |
| CloudFront | 同時30人の規模では性能上の必要性がない。構成の単純さを優先（5.1） |
| 別リージョンへのバックアップ複製 | 要件5.20で明示的に「行わない」とされている |
| アップロードファイルのウイルススキャン | 要件に定めがなく、費用とスコープの判断として見送り。受け入れるリスクは5.4に明記（5.4） |
