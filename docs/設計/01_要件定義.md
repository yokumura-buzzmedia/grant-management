# 助成金管理システム 要件定義書

## 1. この文書について

本書は、助成金管理システムの目的と対象範囲を段階的に合意するための文書です。
一度に詳細を決めず、確認済みの内容から少しずつ追記します。

- 文書状態: 更新中
- 作成日: 2026-08-28
- 今回の確認範囲: システムの目的、アクター、基本業務フロー

## 2. システムの目的（仮）

特定の助成金について、申請に必要な書類の回収、関係者間のやりとり、申請ステータスを一元管理することを目的とします。

想定している効果は次のとおりです。

- 申請に必要な書類と回収状況を把握できる
- 案件ごとの現在のステータスを確認できる
- 関係者が必要なやりとりを行い、次のステータスへ進められる
- 現行システムの複雑さを解消し、安定した業務運用を実現する

## 3. アクター

- クライアント
- システム管理者
- 事務員
- 講師
- 社会保険労務士（社労士）
- 代理店

すべてのアクターが、DBに登録されたそれぞれのアカウントでシステムにログインします。
1つのアカウントには、事務員兼講師など、複数のアクター権限を設定できます。
申請業務全体は、主に事務員と社労士が進めます。

### 3.1 アクター別の役割

| アクター | 主な役割 |
| --- | --- |
| クライアント | 自社情報と自社の申請案件の閲覧・編集、必要書類の提出、講義スケジュールの予約 |
| 事務員 | 申請業務全体の主担当、すべてのクライアントと申請案件の閲覧・編集 |
| 講師 | 自分が担当する講義スケジュールの確認 |
| 社労士 | すべてのクライアントと申請案件の閲覧、確認、コメントによる事務員のフォロー（案件の編集は不可） |
| 代理店 | 自社が紹介した会社の申請案件の進捗確認（閲覧のみ。編集・コメントは不可） |
| システム管理者 | アカウント管理、設定変更、誤操作時のデータ修正 |

## 4. 現行システムの課題

現在は自作のWebアプリを使用していますが、次の課題があるため新システムへリプレイスします。

- 機能が多く、システム全体を把握しきれない
- 不具合が多く、安定した業務運用が難しい

## 5. 基本業務フロー

申請案件は、営業開始から支給申請まで、次の順序で進めます。
ステータスは申請案件が保持し、**会社にステータスを持たせる概念はありません**。
遷移条件と未整理の論点は `11_ステータスの遷移.drawio` にまとめています。

1. 営業中
2. 内諾
3. 助成金説明済
4. 契約書送付済
5. 契約締結済
6. 必要事項記入中
7. 雇用契約書提出中
8. 雇用契約書提出済
9. 日程調整済
10. カリキュラム選定済
11. 見積もり兼発注書送付済
12. 見積もり兼発注書受領済
13. GBiz案内済
14. GBiz記入済
15. 請求書送付済
16. 計画届済
17. 入金確認済
18. 研修中
19. 研修完了
20. 支給申請連絡済
21. 必要書類収集中
22. 必要書類収集完了
23. 助成金の支給申請完了
24. 完了

助成金の受給までには半年から1年程度のラグがあるため、本システムでは受給を確認せず、支給申請の完了をもって「完了」として扱います（5.11）。

完了後に問い合わせが発生した場合は、次の状態へ変更します。

25. 問い合わせ

問い合わせの対応が終わったら「完了」へ戻します。**これは本フローで唯一、前の状態へ戻る遷移です。**

GBiz・計画届・支給申請の各工程は本書の以降の節に記述がありません。詳細は第6章-3の要検討事項とします。

### 5.1 ステータスの変更ルール

- ステータスを主に次へ進めるのは事務員とする
- ステータスは決められた順序で進める
- 原則として、前のステータスには戻せない
- ただし「完了」と「問い合わせ」の間だけは、双方向に変更できる
- 原則として、途中のステータスを飛ばせない
- 事務員が手動で次のステータスへ進める
- ステータスの自動変更は原則として行わない
- **例外として、契約書に関する2つの遷移は自動で進める**
  （後から追加した運用上の判断。いずれも直前のステータスにいるときだけ進め、順序は飛ばさない）
  - 送付に成功したら「3 助成金説明済」→「4 契約書送付済」
  - freeeサイン上で締結を確認できたら「4 契約書送付済」→「5 契約締結済」
- 誤操作時のみ、システム管理者がステータスを修正できる

なお、ステータスの構成と遷移条件の詳細は、第6章の要検討事項として後日詰めます。本節と5章冒頭の12段階は暫定です。

現時点の整理（各ステータスへ進む条件、戻さないケース、要検討事項）は `11_ステータスの遷移.drawio` に集約しています。

### 5.2 必要書類の提出・確認フロー

本システムで扱う必要書類は次の2種類です。**申請案件ごとに提出する「案件共通の書類」は設けません。**

| 種類 | 紐づく先 | 収集する区間 |
| --- | --- | --- |
| 受講者別の書類（雇用契約書） | 会社（受講者） | ステータス「雇用契約書提出中」〜「雇用契約書提出済」 |
| 支給申請用の書類 | 申請案件 | ステータス「必要書類収集中」〜「必要書類収集完了」 |

**提出と確認の流れ**

1. クライアントが必要書類を提出する。
2. 事務員が提出書類の内容を確認する。
3. 問題がなければ、事務員が書類を承認する。
4. 不備がある場合は、事務員が不備内容をコメントし、クライアントへ再提出を依頼する。
5. クライアントが修正した書類を再提出する。

**共通のルール**

- 必要書類の種類と名称は、システム内のマスタではなくコード側で固定して管理する
- 管理画面に、必要書類を追加・変更・削除する機能は設けない
- 必要書類の追加・変更・削除は、システムのリリース（開発対応）で行う
- 書類の構成は全申請案件で常に共通とし、申請案件ごとに個別の書類構成は保持しない
- 必要書類を追加・削除した場合は、進行中の申請案件にも即時反映する
- 必要書類の追加により、すでに収集を完了した申請案件に未提出の書類が生じた場合でも、ステータスは前へ戻さない
- 1種類の必要書類につき、提出できるファイルは1つとする
- 提出できるファイル形式はPDF、JPEG、PNGとする
- 1ファイルあたりの最大容量は50MBとする
- 承認済みの書類が差し替えられた場合は、承認を取り消し、事務員による再承認を必要とする
- クライアントが書類を提出または再提出したときは、事務員へシステム内で通知する
- 書類の差し替え前のファイルと提出履歴は保存しない

**受講者別の書類（雇用契約書）**

- 受講者一人ひとりの雇用契約書を提出する
- 受講者1人につき1ファイルを提出する
- 申請案件ではなく受講者データ（会社）に紐づけて管理する
- 同じ会社の別の申請案件では、提出済みの雇用契約書をそのまま使い回す
- 提出対象はその会社に登録されているすべての受講者とし、申請案件やチームへの登録有無では絞り込まない
- 会社に登録されているすべての受講者の雇用契約書が承認済みになるまで、事務員はステータスを「雇用契約書提出済」へ進められない
- 承認は会社単位で一度だけ行い、同じ会社のすべての申請案件で承認済みとして扱う
- 会社に受講者を追加した場合は、その会社の進行中のすべての申請案件で、追加した受講者の雇用契約書が承認されるまでステータスを次へ進められない
- すでに「雇用契約書提出済」以降へ進んでいる申請案件のステータスは、受講者の追加によって前へ戻さない
- 承認済みの雇用契約書を差し替えた場合は、同じ会社のすべての申請案件で承認を取り消し、事務員による再承認を必要とする

**支給申請用の書類**

- 助成金の支給申請に必要な書類を、申請案件ごとに提出する
- すべての支給申請用の書類が承認済みになるまで、事務員はステータスを「必要書類収集完了」へ進められない
- 具体的な名称と種類は要確認とする

### 5.3 会社情報の登録・編集

事務員またはシステム管理者が会社データを作成し、最初に会社名だけを入力します。
招待されたクライアントが、会社名以外の会社基本情報を入力します。
最終的には、次のすべての項目を必須とします。
ただし、一時保存を可能にするため、会社情報のDBカラムはNULLを許容します。

| 項目 | 必須 |
| --- | --- |
| 会社名 | はい |
| 法人番号 | はい |
| 代表者名 | はい |
| 業種 | はい |
| 会社形態 | はい |
| 従業員数 | はい |
| 資本金 | はい |
| 郵便番号 | はい |
| 住所 | はい |
| 建物名 | はい |
| 電話番号 | はい |
| 担当者名 | はい |
| 担当者メールアドレス | はい |

- 1社に複数のクライアントアカウントを登録できる
- 1つのクライアントアカウントは、1社だけに所属する
- クライアントアカウントの作成後は、所属会社を変更しない
- 有効なクライアントアカウントが0件になっても、会社データは削除せず残す
- 同じ法人番号を持つ会社データは、重複して登録できない
- 法人番号は、半角数字13桁のみ入力できる
- 担当者メールアドレスは、メールアドレス形式の検証を行う
- 郵便番号は、ハイフンを含まない半角数字7桁のみ入力できる
- 郵便番号を入力したときは、対応する住所を自動入力する
- 郵便番号から自動入力された住所は、利用者が修正できる
- 郵便番号に対応する住所を取得できない場合は、住所を手入力できる
- 電話番号は、数字部分を10桁または11桁とし、入力時のハイフンを許可する
- 業種は、選択式ではなく自由入力とする
- 会社形態は、「株式会社」「合同会社」「合資会社」「合名会社」「個人事業主」「その他」から選択する
- 従業員数は、0以上の整数のみ入力できる
- 資本金は、0円以上の整数のみ入力できる
- クライアントは、登録後も自社の会社情報を編集できる
- 事務員とシステム管理者も、会社情報を入力・編集できる
- クライアントは、必須項目が未入力の状態でも会社情報を一時保存できる
- 会社情報の必須項目が未入力でも、事務員またはシステム管理者は申請案件を作成できる
- 会社情報の必須項目がすべて入力され、かつ受講者が1人以上登録されるまで、申請案件のステータスを最初の「契約書送付」へ進めることはできない
- 未入力項目または受講者の未登録があるため「契約書送付」へ進められない場合は、その内容を画面に表示する
- 「契約書送付」以降の申請案件が1件でもある会社では、必須項目を未入力の状態へ戻す編集を禁止する
- 会社データは、事務員またはシステム管理者が削除できる
- クライアントは、会社データを削除できない
- 申請案件が紐づいている会社データも削除できる
- 会社データは完全削除とし、削除後は復元できない
- 会社データを完全削除する前に、確認ダイアログを表示する
- 会社データを削除した場合は、その会社に紐づく申請案件と案件専用データもすべて完全削除する
- 会社データを削除した場合は、その会社に紐づくクライアントアカウントと受講者情報もすべて削除する
- 会社データの削除時に、削除理由の入力は求めない
- 会社データを削除しても、「削除した利用者」「削除日時」「会社名」「法人番号」の削除履歴は保存する
- 会社の削除履歴は、事務員とシステム管理者が閲覧できる
- 保存した会社の削除履歴は、事務員とシステム管理者のどちらも削除できない
- 会社一覧には、「会社名」「法人番号」「担当者名」「電話番号」「最終更新日時」を表示する
- 会社一覧では、会社名と法人番号による検索を行える
- 会社一覧の初期表示順は、作成日時が新しい順とする
- 会社一覧の列見出しを選択し、会社名や最終更新日時などの列で並び替えられる
- 会社一覧はページ分割し、1ページあたり50件を表示する
- 会社情報の必須項目がすべて入力済みかを示す「入力完了・未完了」の表示や絞り込みは設けない
- 担当者名と担当者メールアドレスは、ログインアカウントとは別の会社主担当者情報として管理する
- クライアントが会社情報を変更しても、事務員への通知は送らない

### 5.4 アカウントの作成・ログイン

- クライアントアカウントは、システム管理者または事務員が作成し、クライアントを招待する
- クライアントによる自由な新規アカウント登録は行わない
- 講師、社労士、代理店のアカウントは、システム管理者または事務員が作成する
- 事務員アカウントは、システム管理者が作成する
- システム管理者アカウントも、他のアクターと同様にDBで管理する
- システム管理者アカウントは、複数登録できる
- 新しいシステム管理者アカウントは、既存のシステム管理者が作成する
- ログインIDにはメールアドレスを使用しない
- ログインIDは、アカウント作成者が任意の文字列を設定する
- すべてのアカウントに、画面表示用の利用者名を必須項目として登録する
- ログインIDは、アクターの種類に関係なくシステム全体で重複不可とする
- ログインIDは大文字と小文字を区別する（「Tanaka」と「tanaka」は別のログインIDとして扱う）
- アカウント作成後も、事務員またはシステム管理者がログインIDを変更できる
- 事務員は、システム管理者以外のアカウントのログインIDを変更できる
- システム管理者は、すべてのアカウントのログインIDを変更できる
- 利用者本人も、自分のログインIDを変更できる
- ログインIDに使用できる文字は、半角英数字と「-」「_」とする
- ログインIDは、6文字以上20文字以下とする
- 利用者本人がログインIDを変更するときは、現在のパスワード入力を必須とする
- ログインIDを変更した後は、利用者をログアウトさせ、新しいログインIDでの再ログインを必要とする
- 変更前のログインIDは、別のアカウントで再利用できる
- アカウント作成時に、システムが仮パスワードを自動発行する
- 利用者は、自動発行された仮パスワードで初回ログインする
- 初回ログイン後は、利用者自身が新しいパスワードを必ず設定する
- 新しいパスワードを設定するまで、通常のシステム機能は利用できない
- 利用者は、ログイン後にいつでも自分の通常パスワードを変更できる
- 通常パスワードの変更時に、現在のパスワード入力は求めない
- 新しいパスワードは、確認用を含めて同じ内容を2回入力する
- パスワードを忘れた場合、利用者自身によるパスワード再設定は行わない
- システム管理者または事務員が、仮パスワードを再生成する
- 再生成した仮パスワードは、メールまたはLINEで利用者に個別に伝える
- 仮パスワードでログインした場合は、発行理由を問わず、利用者自身による新しいパスワードの設定を必須とする
- 仮パスワードに有効期限は設けない
- 事務員は、事務員、クライアント、講師、社労士、代理店のアカウントに対して仮パスワードを再生成できる
- 事務員は、システム管理者の仮パスワードを再生成できない
- クライアント、講師、社労士、代理店のアカウントは、事務員またはシステム管理者が無効にできる
- 事務員アカウントは、事務員またはシステム管理者が無効にできる
- ただし、完了していない申請案件の主担当に設定されている事務員アカウントは無効にできない
- 無効にしたアカウントは、システムへログインできない
- クライアント、講師、社労士、代理店の無効なアカウントは、事務員またはシステム管理者が再び有効にできる
- 事務員の無効なアカウントも、事務員またはシステム管理者が再び有効にできる
- システム管理者は、別のシステム管理者アカウントを無効にできる
- システム管理者は、自分自身のアカウントを無効にできない
- 有効なシステム管理者が1人だけの場合、そのシステム管理者アカウントは無効にできない
- 無効にしたシステム管理者アカウントは、別の有効なシステム管理者が再び有効にできる
- アカウントには、事務員兼講師など複数の権限を設定できる
- アカウント作成後も、設定されている権限を追加・変更・解除できる
- 複数の権限が設定されたアカウントは、各権限で許可されている操作をすべて利用できる
- アカウント単体を完全削除する機能を設ける
- システム管理者は、すべてのアカウントを完全削除できる
- 事務員は、システム管理者権限が設定されていないアカウントを完全削除できる
- アカウントを完全削除する前に、確認ダイアログを表示する
- アカウントの完全削除時に、削除理由の入力は求めない
- アカウントを完全削除しても、「削除した利用者」「削除日時」「削除対象の利用者名」「削除対象のログインID」の削除履歴は保存する
- アカウントの削除履歴は、事務員とシステム管理者が閲覧できる
- 保存したアカウントの削除履歴は、事務員とシステム管理者のどちらも削除できない
- システム管理者は、自分自身のアカウントを完全削除できる
- ただし、有効なシステム管理者が1人だけの場合、そのシステム管理者アカウントは完全削除できない
- 完了していない申請案件の主担当になっている事務員アカウントは、主担当を別の有効な事務員へ変更するまで完全削除できない
- 今後の確定済み予約を担当している講師アカウントは、講師の担当変更または予約取消が完了するまで完全削除できない
- 完了していない申請案件の主担当になっているアカウントは、主担当を別の有効な事務員へ変更するまで事務員権限を解除できない
- 今後の確定済み予約を担当しているアカウントは、講師の担当変更または予約取消が完了するまで講師権限を解除できない
- 有効なシステム管理者が1人だけの場合、そのアカウントのシステム管理者権限は解除できない
- クライアントアカウント（ユーザーID）を完全削除しても、所属会社、申請案件、提出書類などの業務データは削除せず残す
- アカウントを完全削除しても、過去の申請案件、掲示板投稿、予約などに表示される利用者名は残す
- アカウントを無効にしても、過去の申請案件、掲示板投稿、予約などに表示される利用者名は残す
- 通常パスワードは8文字以上とする
- 通常パスワードは20文字以下とする
- 通常パスワードには、半角英数字と半角記号を使用できる
- 通常パスワードには、半角英字と半角数字をそれぞれ1文字以上含める
- 半角記号の使用は任意とする
- 文字種の条件を満たさない場合は、その内容を画面に表示し、設定を受け付けない
- 文字種の条件は、初回ログイン時の設定と、その後の変更のどちらにも適用する
- 現在または過去に使用した通常パスワードの再利用を許可する
- アカウント一覧には、「利用者名」「ログインID」「権限（複数可）」「所属会社」「有効／無効」「最終更新日時」を表示する
- アカウント一覧では、利用者名とログインIDによる検索を行える
- アカウント一覧では、権限と有効／無効による絞り込みを行える
- システム管理者は、すべてのアカウントを一覧で閲覧できる
- 事務員は、システム管理者以外のアカウントを一覧で閲覧できる
- アカウント一覧の初期表示順は、作成日時が新しい順とする
- アカウント一覧の列見出しを選択し、利用者名や最終更新日時などの列で並び替えられる
- アカウント一覧はページ分割し、1ページあたり50件を表示する
- アカウント一覧の初期表示には、有効なアカウントだけを表示する
- ログインに多要素認証は使用しない
- ログイン失敗が連続しても、アカウントの自動ロックは行わない

仮パスワードの有効期限、パスワードの条件、通常パスワード変更時の本人確認、多要素認証、アカウントロックは、上記のとおり確定とします。運用開始後にセキュリティ要件が変わった場合は、改めて見直します。

### 5.5 講義スケジュールの予約

1. システムは、土曜日、日曜日、祝日を予約不可日とする。
2. 個別に登録された休業日も予約不可日とする。
3. 予約不可日以外を、クライアントが選択できる予約可能日とする。
4. 講義の空き日程は個別に登録しない。
5. 個別の休業日は、事務員またはシステム管理者が登録・変更する。
6. クライアントは、全10時間の講義を2日間、3日間、4日間、5日間のいずれで受講するかを選択する。
7. クライアントは、選択した日数分の講義日と各日の開始時刻を選択し、予約を申請する。
8. システムは、選択した日数ごとの講義時間配分に従い、各日の終了時刻を自動計算する。
9. 2日間で受講する場合は、1日あたり5時間とする。
10. 3日間で受講する場合は、3時間、3時間、4時間の順とする。
11. 4日間で受講する場合は、1日あたり2時間30分とする。
12. 5日間で受講する場合は、1日あたり2時間とする。
13. クライアントは特定の申請案件を選択し、その申請案件に紐づく予約枠を作成する。予約申請時点ではチームを登録しない。
14. 予約枠作成後に、事務員またはシステム管理者がチームを作成する。
15. 1つの予約枠に対して1つのチームを作成し、予約枠とチームを紐づける。
16. チーム作成後に、事務員またはシステム管理者がチームのカリキュラムを登録する。
17. 事務員は予約申請を承認するときに、担当講師を指定する。
18. 事務員の承認と担当講師の指定後に、講義スケジュールを確定する。
19. 1人の講師に、同じ日時の講義を重複して割り当てることはできない。
20. 予約の承認と担当講師の決定時に、クライアントと担当講師へシステム内通知を送る。
21. 同じ日時でも、別の講師を割り当てられる場合は、複数のクライアントの予約を承認できる。
22. 同一日時に確保できる予約枠数の上限は、「講師マスタの有効な講師数 - 1」とする。
23. クライアントが予約を申請した時点で、事務員の承認前でも予約枠を1つ確保する。
24. 講師マスタの有効な講師数が減り、新しい上限を超えた場合でも、すでに受け付けた予約は維持する。
25. 予約申請の承認前は、クライアントが予約日時を変更または予約をキャンセルできる。
26. 予約確定後の日時変更・キャンセルは、事務員またはシステム管理者だけが行える。
27. 予約がキャンセルまたは却下された場合は、確保していた予約枠をすぐに解放する。
28. 予約がキャンセルまたは却下されても、すでに作成されたチームは削除せず保存する。
29. 予約申請を却下する場合は、却下理由のコメントとクライアントへのシステム内通知は行わない。
30. 予約確定後に日時を変更または予約をキャンセルした場合は、クライアントと担当講師へシステム内通知を送る。

### 5.6 申請案件・チーム・カリキュラムの関係

- 1顧客（1社）は、複数の申請案件を持つことができる
- 1つの申請案件は、複数のチームを持つことができる
- 1つの申請案件は、複数の予約枠を持つことができる
- 1チームに登録できるカリキュラムは1つとする
- 1つのカリキュラムに対して、複数の講義日を予約できる
- チームは、事務員またはシステム管理者が作成する
- チームは、クライアントによる講義予約の後に作成する
- 予約申請時点では、仮のチームやチーム予定データは登録せず、予約枠だけを作成する
- 1つの予約枠から1つのチームを作成し、予約枠とチームを紐づける
- 予約がキャンセルまたは却下された後に残したチームは、新しい予約枠に紐づけて再利用できる
- チームの基本情報として、チーム名と受講者を登録する
- 受講者情報の初回登録は、クライアントが会社の基本情報を登録するときに、同じタイミングで行う
- 受講者の登録は、講義予約やチームの作成を待たずに行える
- 初回登録後の受講者情報は、クライアント、事務員、システム管理者が編集・削除できる
- 受講者の登録項目は、「氏名」「フリガナ」「雇用保険被保険者番号」「雇用形態」「職種」「職務内容」「性別」とする
- 受講者の登録項目は、7項目すべてを必須とする
- 氏名は自由入力とする
- フリガナは全角カタカナのみ入力できる
- 雇用保険被保険者番号は、ハイフンを含まない半角数字11桁のみ入力できる
- 雇用形態は、「正社員」「契約社員」「パート・アルバイト」「派遣」「その他」から選択する
- 職種と職務内容は自由入力とする。職種はカリキュラムの職種カテゴリマスタとは別のものとする
- 性別は、「男性」「女性」「その他」から選択する
- 同じ会社の中では、同じ雇用保険被保険者番号の受講者を重複して登録できない
- 別の会社であれば、同じ雇用保険被保険者番号の受講者を登録できる
- 1チームあたりの受講者数に、最小・最大人数の制限は設けない
- 受講者は顧客（会社）に紐づけて管理する
- 一度登録した受講者は、同じ顧客の別の申請案件で再利用できる
- 同じ申請案件内では、1人の受講者を複数のチームに重複して登録できない
- 受講者がチームに登録済みの場合でも、受講者情報自体を削除できる
- 受講者を削除した場合は、所属しているチームからも自動で削除する
- 受講者を削除した場合は、その受講者の雇用契約書も削除する
- 受講者を削除した場合は、研修完了後の過去記録にも受講者の名前を残さない

### 5.7 カリキュラム管理

カリキュラムは、「研修プログラム」「職種カテゴリ」「コース」「講義コマ」「開催パターン」「パターン日別コマ割当」の6つのマスタで構成します。

**マスタ共通のルール**

- 研修プログラム、職種カテゴリ、コース、開催パターンは、それぞれ独立したマスタとして管理する
- 名称は文字列としてコースやチームのデータに持たせず、マスタのコードで参照する
- 各マスタは一意のコードを持ち、コードは登録後に変更しない
- マスタの登録・変更・削除のルールは、後述の「マスタの変更・削除」に従う

**研修プログラムマスタ**

- 登録項目は、「研修プログラムコード」「研修プログラム名」「段階」「表示順」とする
- 「生成AI活用研修（第1段階）」「AIエージェント活用研修（第2段階）」の2件を登録する

**職種カテゴリマスタ**

- 登録項目は、「職種カテゴリコード」「職種カテゴリ名」「表示順」とする
- 「バックオフィス系」「営業系」「マーケティング・クリエイティブ系」「福祉・医療系」「現場・技能系」「サービス系」「専門職・企画系」の7件を登録する

**コースマスタ**

- 登録項目は、「研修プログラム」「職種カテゴリ」「コース番号」「職種名」「目的」「表示順」とする
- 研修プログラムと職種カテゴリは、それぞれのマスタから選択する
- コースは職種ごとに用意し、1つの研修プログラムにつき66コース、全体で132コースとする
- 目的はプレーンテキストで登録し、文字装飾は保持しない

**講義コママスタ**

- 講義コマは、コースマスタに紐づけて管理する
- 登録項目は、「コマ記号」「表示順」「所要時間」「タイトル」「説明」とする
- 1つのコースは複数の講義コマで構成し、コマ数はコースごとに決める
- 所要時間は0.5時間単位で登録する
- 1コースの講義コマの所要時間の合計は、10時間とする

**開催パターンマスタ**

- 登録項目は、「開催パターンコード」「開催パターン名」「受講日数」「時間内訳」「表示順」とする
- 「2日間」「3日間」「4日間」「5日間」の4件を登録する
- パターン日別コマ割当として、開催パターンごとに各講義日へ割り当てる講義コマを定義する
- 講義コマの割当は、開催パターンとコースの組み合わせごとに定義する
- クライアントが選択する受講日数は、開催パターンマスタから選択する

**マスタの変更・削除**

- チームにコースを紐づけた時点で、コースの内容、講義コマの内容、開催パターンの日別コマ割当をチームに複製して保持する
- 紐づけ後にマスタを変更しても、すでに紐づけ済みのチームが保持する内容は変更しない
- 研修プログラム名と職種カテゴリ名は複製せず、マスタの最新の名称を表示する
- 新しくチームに紐づける場合は、変更後の最新のマスタの内容を複製する
- どのチームからも参照されていないマスタは削除できる
- チームから参照されているマスタは削除できず、「無効」にして新規の選択肢から外す
- 無効にしたマスタを参照している既存のチームの内容・記録は、そのまま維持する
- 無効にしたマスタは、再び有効に戻せる

**運用**

- カリキュラムの各マスタは、事務員またはシステム管理者が登録・編集する
- クライアントは、カリキュラムのマスタを登録・編集しない
- 事務員またはシステム管理者が、クライアントによる講義日時の予約後に、コースをチームに登録する
- チームには、研修プログラムとコースの組み合わせ（132通り）から1つを選択して紐づける
- 管理画面にCSVインポート機能を設け、各マスタを一括で登録・更新できるようにする
- CSVは、マスタごとに1ファイルとする（研修プログラム／職種カテゴリ／コース／講義コマ／開催パターン／パターン日別コマ割当）
- カリキュラムの初期データは、CSVインポートで登録する
- パターン日別コマ割当のCSVはコマ記号ごとの雛形とし、取り込み時に全コースへ展開する。すでに割当のあるコースは変更しない
- 初期データのCSVは `docs/data/` に格納する

### 5.8 契約書送付・契約締結

- 契約書の作成には、外部の電子契約サービス「FREE SIGN」を使用する
- 契約書は、FREE SIGNにあらかじめ登録したテンプレートから生成する
- テンプレートの登録・保守は、事務員がFREE SIGNの画面で行う
- 本システムにテンプレートの作成・編集機能は設けない
- 会社名など、契約書の送付時点では確定していない項目は、クライアントが署名時にFREE SIGN上で入力する
- 契約締結は、FREE SIGN上で行う
- 事務員が本システムで送付操作を実行すると、FREE SIGNからクライアントへ署名依頼メールを送信する
- 署名依頼メールは本システムからは送信せず、FREE SIGNからの送信のみとする
- 契約書の送付先は、会社情報の「担当者メールアドレス」とする
- クライアントは、本システムにログインせずに署名依頼メールから署名できる
- 本システムとFREE SIGNは自動連携する
- FREE SIGNで締結済みとなった契約書のPDFを、本システムに保存する
- FREE SIGNで契約締結を確認した後、事務員が本システムのステータスを手動で「契約締結」へ進める
- 事務員が本システムで契約書の送付操作を実行したときに、FREE SIGNへ契約書の作成・送付を連携する
- FREE SIGNで契約締結が完了したら、本システムが締結済みPDFを自動取得して保存する
- 事務員は、本システムから署名依頼メールの再送を実行できる
- 再送は同じ契約書に対して行い、送付先は初回と同じ「担当者メールアドレス」とする
- 未署名のまま一定期間が経過しても、自動での催促メールは送信しない
- 送付後に契約書の内容を修正する場合は、事務員が本システムから送付を取り消す
- 送付を取り消すと、FREE SIGN側の署名依頼も無効にする
- 送付を取り消しても、申請案件のステータスは「契約書送付」のままとし、前へ戻さない
- 送付を取り消した後は、内容を修正して改めて送付できる
- 締結済みの契約書は、送付の取り消しも再送もできない
- 1つの申請案件に登録する契約書は1つとする
- FREE SIGNとの自動連携方法と利用可能なAPIは、技術設計時の確認事項とする

### 5.9 見積もり兼発注書の送付・回収

- 見積書と発注書は別ファイルとせず、1つの「見積もり兼発注書」とする
- 見積もり兼発注書は、本システムが登録データから自動生成する
- 見積もり兼発注書を生成しただけでは、クライアントへ送付しない
- 事務員が本システムで送付操作を実行したときだけ、見積もり兼発注書をクライアントへ送付する
- 見積もり兼発注書は、メールでクライアントへ送付する
- 見積もり兼発注書の送付先は、会社情報の「担当者メールアドレス」とする
- 署名・押印済みの見積もり兼発注書は、クライアントが本システムにアップロードして提出する
- アップロードできるファイル形式と最大容量は、必要書類と同じくPDF・JPEG・PNG、50MBとする
- 提出できるファイルは1つとし、差し替えた場合は前のファイルと提出履歴を保存しない
- クライアントがアップロードしたときは、事務員へシステム内で通知する
- 事務員は、アップロードされた内容を確認したうえで、手動でステータスを次へ進める
- 事務員は、不備がある場合にコメントを添えてクライアントへ再提出を依頼できる
- 1つの申請案件に登録する見積もり兼発注書は1つとする

### 5.10 請求書送付・入金確認

- 請求書は、本システムが登録データから自動生成する
- 請求書を生成しただけでは、クライアントへ送付しない
- 事務員が本システムで送付操作を実行したときだけ、請求書をクライアントへ送付する
- 請求書の送付先は、会社情報の「担当者メールアドレス」とする
- 入金を確認した後、事務員が申請案件のステータスを手動で「入金確認済」へ進める

### 5.11 研修開始から完了まで

- 申請案件のステータスは、事務員が手動で「研修中」へ進める
- 申請案件のステータスは、事務員が手動で「研修完了」へ進める
- 助成金の受給までには半年から1年程度のラグがあるため、本システムでは受給を確認しない
- 助成金の支給申請が完了した後、事務員が申請案件のステータスを手動で「完了」へ進める
- 「完了」の後に問い合わせが発生した場合は「問い合わせ」へ変更し、対応が終われば「完了」へ戻す
- 各講義日の「実施済み」「中止」などの実施結果は、本システムに記録しない

**出欠の記録**

- 受講者ごとの出欠は、すべての受講者を「出席」として扱うことを既定とする
- 出席の場合は、講師・事務員とも入力を行わない
- 遅刻・早退・欠席が発生した場合のみ、専用のメニューから記録する
- 記録項目は、「講義日」「チーム」「受講者」「区分（遅刻・早退・欠席）」「備考」とする
- 出欠の記録がない受講者は、すべて出席とみなす
- 遅刻・早退・欠席の記録は、講師と事務員の両方が登録・編集・削除できる
- 講師が記録できるのは、自分が担当する講義日のみとする
- 事務員は、すべての講義日の記録を登録・編集・削除できる
- クライアントは、自社の申請案件の記録を閲覧できるが、登録・編集はできない
- 遅刻・早退の時刻や、受講できなかった時間は記録しない
- 補足が必要な場合は、備考に自由入力で記録する
- 欠席者への振替受講など、欠席後のフォローを本システムで扱うかは要確認とする

### 5.12 案件掲示板

- 申請案件ごとに、案件全体についてやり取りする掲示板を設ける
- 提出書類ごとに個別のコメント欄は設けない
- その申請案件を閲覧できるすべてのアクターが、掲示板を閲覧し投稿できる
- ただし代理店は、掲示板を閲覧できるが、投稿はできない
- 掲示板の新しい投稿には、共通のシステム内通知機能を使用しない
- 掲示板に未読の投稿がある場合は、案件画面の掲示板タブに未読バッジを表示する
- 自分以外の利用者による新しい投稿だけを、未読バッジの対象とする
- 利用者が掲示板タブを開いた時点で、その掲示板の投稿を既読にして未読バッジを消す
- 投稿者は、自分の投稿を編集・削除できる
- 掲示板の投稿には、ファイルを添付できる
- 添付できるファイル形式は、PDF、JPEG、PNGとする
- 添付ファイルの最大容量は、1ファイルあたり50MBとする

### 5.13 共通通知

- 書類提出や予約確定などの通知は、画面上部のベルアイコンから一覧表示する
- ベルアイコンには、未読通知の件数をバッジで表示する
- 利用者が通知を選択した場合は、通知内容に対応する申請案件または予約画面へ移動する
- 利用者が通知を選択した時点で、その通知を既読にする
- 通知一覧に「すべて既読にする」操作を設ける
- 過去の通知は自動削除せず、すべて保存する
- 案件掲示板の新しい投稿は、共通通知の対象に含めない

### 5.14 ダッシュボード・案件一覧

- 事務員、システム管理者、社労士には、ログイン後の最初の画面としてダッシュボードを表示する
- 事務員とシステム管理者のダッシュボードには、ステータスごとの案件数を表示する
- 社労士のダッシュボードには、事務員と同じステータスごとの案件数を閲覧専用で表示する
- クライアントには、ダッシュボードを設けない
- クライアントは、ログイン後の最初の画面として自社の申請案件一覧を表示する
- 講師には、ダッシュボードを設けない
- 講師は、ログイン後の最初の画面として自分が担当する講義スケジュールを表示する
- 代理店には、ダッシュボードを設けない
- 代理店は、ログイン後の最初の画面として自社が紹介した会社の申請案件一覧を表示する
- ダッシュボードのステータス別案件数を選択すると、選択したステータスで絞り込んだ案件一覧へ移動する
- 案件一覧では、会社名による検索を行える
- 案件一覧では、案件番号と案件名による検索を行える
- 案件一覧では、申請案件のステータスによる絞り込みを行える
- 案件一覧では、主担当事務員による絞り込みを行える
- 案件一覧には、「案件番号」「会社名」「案件名」「主担当事務員」「現在のステータス」「最終更新日時」を表示する
- 案件一覧の初期表示順は、案件番号の降順とする
- 案件一覧の列見出しを選択し、案件番号や最終更新日時などの列で並び替えられる
- 案件一覧はページ分割し、1ページあたり50件を表示する

### 5.15 申請案件の作成・削除

- 申請案件は、事務員またはシステム管理者が作成する
- 申請案件は、営業を開始した時点（ステータス「営業中」）で作成する
- 申請案件の作成時に、システムが案件番号を自動発行する
- 申請案件は、事務員またはシステム管理者が削除できる
- クライアント、講師、社労士、代理店は、申請案件を作成・削除できない
- 申請案件を削除する場合は、データを残さず完全に削除する
- 削除した申請案件は復元できない
- 申請案件は、現在のステータスに関係なく削除できる
- 進行中または完了済みの申請案件も削除できる
- 完全削除を実行する前に、確認ダイアログを表示する
- 申請案件を削除した場合は、その案件専用の書類、予約、チーム、掲示板投稿などの関連データもすべて削除する
- 申請案件を削除しても、会社情報とクライアントアカウントは削除せず残す
- 申請案件を削除しても、会社に紐づく受講者情報は削除せず残す
- 申請案件の削除時に、削除理由の入力は求めない
- 申請案件を削除しても、「削除した利用者」「削除日時」「案件番号」「会社名」の削除履歴は保存する
- 削除履歴は、事務員とシステム管理者が閲覧できる
- 保存した削除履歴は、事務員とシステム管理者のどちらも削除できない

### 5.16 申請案件の基本情報・担当者

- 自動発行する案件番号とは別に、申請案件名を必須項目として登録する
- 申請案件の作成時に、主担当の事務員を1人必ず設定する
- 申請案件の作成後も、事務員またはシステム管理者が主担当の事務員を変更できる
- 主担当には、有効な事務員アカウントだけを指定できる
- 主担当の設定または変更時に、新しい主担当への共通通知は送らない
- 完了していない申請案件の主担当に設定されている事務員アカウントは、無効にできない
- 未完了案件の主担当をすべて別の有効な事務員へ変更した後は、元の事務員アカウントを無効にできる
- 事務員アカウントを無効にしても、完了済み案件には主担当者名を履歴として残す
- 無効にした事務員アカウントは、事務員またはシステム管理者が再び有効にできる
- 申請案件ごとの担当社労士は設定しない
- 社労士は、担当者として割り当てられていなくてもすべての申請案件を閲覧・確認できる

### 5.17 更新情報

- ステータス変更に限らず、会社情報、申請案件、書類、予約などの更新対象データには、最終更新日時と最終更新者を保存する
- 更新のたびに履歴を追加する方式ではなく、最新の更新日時と更新者だけを保持する
- 会社情報や申請案件の基本情報について、変更前後の内容は保存しない
- 操作履歴を一覧表示・閲覧する機能は設けない
- システムの自動処理がデータを更新した場合は、最終更新者を「システム」として保存する
- 各データの詳細画面に、最終更新日時と最終更新者を表示する
- 各データには、最終更新情報とは別に作成日時と作成者も保存する
- 申請案件の削除履歴は、完全削除後も残す必要があるため例外として保存する

### 5.18 利用環境

- パソコンとスマートフォンの両方で利用できるWebシステムとする
- スマートフォンではWebブラウザから利用し、専用のスマートフォンアプリは作成しない
- 対応ブラウザは、Google Chrome、Microsoft Edge、Safariの各最新版とする

### 5.19 セッション管理

- 同じアカウントで、複数の端末またはブラウザから同時にログインできる
- 無操作時間による自動ログアウトは行わない
- ブラウザを閉じて再度開いた場合も、ログイン状態を維持する
- ログイン状態の最長有効期間は、ログイン時点から30日間とする
- 利用者が通常パスワードを変更した場合は、変更操作を行った端末を含むすべての端末からログアウトさせる
- システム管理者または事務員が仮パスワードを再生成した場合は、そのアカウントでログイン中のすべての端末からログアウトさせる
- アカウントを無効化または完全削除した場合は、そのアカウントでログイン中のすべての端末から直ちにログアウトさせる
- アカウントの権限を追加・変更・解除した場合は、ログイン中のすべての端末へ変更後の権限を直ちに反映する
- 通常のログアウト操作では、操作した端末だけをログアウトさせる
- 利用者自身が、ログイン中のすべての端末を一括ログアウトする機能は設けない
- システム管理者または事務員が、任意のアカウントを強制ログアウトさせる機能は設けない

### 5.20 インフラ・バックアップ

- インフラストラクチャはAWSの利用を前提とする
- データベースとアップロード済みファイルを、1日1回自動でバックアップする
- バックアップの保存期間は30日間とする
- バックアップは、本番環境と同じAWSアカウント内の専用の保管先に保存する
- バックアップの保管先は、本番環境のデータベースおよびファイル保存先とは別に用意する
- バックアップの保管先には削除保護を設定し、保存期間中は誤って削除できないようにする
- バックアップの保管先へのアクセス権限は、本番環境の実行権限とは分けて設定する
- 別AWSアカウントや別リージョンへの複製は行わない

**不正アクセス対策**

- ログイン画面へのリクエストは、AWS WAFで送信元IPアドレス単位のレート制限を行う
- レート制限は、アカウントの無効化やロックを伴わないものとする
- レート制限の具体的なしきい値は、技術設計時に決定する

### 5.21 想定規模

- 運用開始時の会社数は、約100社を想定する
- 将来的な最大会社数は、約10,000社を想定する
- 1社あたりの申請案件数は、1件から5件を想定する
- 運用開始時のシステム全体の申請案件数は、約100件から500件を想定する
- 将来的なシステム全体の最大申請案件数は、約50,000件を想定する
- 最大同時利用者数は、30人を想定する

### 5.22 性能要件

- 通常の画面表示、検索、保存操作は、原則として3秒以内の応答を目標とする
- 見積もり兼発注書や請求書などのPDF生成は、原則として10秒以内の完了を目標とする
- ファイルアップロード、メール送信、FREE SIGNなどの外部サービスとの通信時間は、3秒・10秒の性能目標から除外する
- 最大50MBのファイルをアップロードするときに、アップロードの進捗状況は表示しない
- 保存、PDF生成、ファイルアップロードなどの処理中は、進捗率を示さないプログレススピナーを表示する
- プログレススピナーの表示中は、処理が完了するまで同じ操作を含む他の操作を行えないようにする
- 保存、PDF生成、ファイルアップロードなどに失敗した場合は、エラーメッセージを表示する
- エラー発生後は、利用者が対象の処理を再実行できるようにする

### 5.23 お知らせ

- 管理画面に、全利用者へ表示するお知らせの編集機能を設ける
- お知らせ編集機能では、お知らせ表示のON・OFFと表示内容を管理する
- お知らせのON・OFFと内容を編集できるのは、システム管理者だけとする
- お知らせの内容には、リンクを設定できる
- お知らせの文字には、「太字」「斜体」「下線」「文字色」「文字サイズ」の装飾を設定できる
- お知らせ本文は、最大1,000文字とする
- お知らせには、画像・動画・ファイルを添付できない
- システム管理者は、お知らせをONにする前に実際の表示内容をプレビューできる
- お知らせがOFFの間も、入力済みの内容と文字装飾を保存して次回編集時に残す
- お知らせをONにする場合は、本文の入力を必須とする
- お知らせがONの状態で内容を保存した場合は、保存完了後すぐに全画面へ変更内容を反映する
- お知らせは、ログイン画面を含むすべての画面に共通バナーとして表示する
- 同時に表示できるお知らせは、1件だけとする
- 利用者は、表示中のお知らせバナーを閉じて非表示にできる
- お知らせを閉じた状態はアカウント単位では保存せず、別の端末やブラウザには共有しない
- お知らせを閉じた状態は現在のブラウザにも保存せず、ページ再読み込みまたはブラウザ再起動後に再表示する
- システム管理者がお知らせ内容を変更した場合は、以前のお知らせを閉じた利用者にも変更後のお知らせを再表示する
- システム管理者がお知らせ内容を変更せずにOFFからONへ戻した場合も、全利用者へお知らせを再表示する
- お知らせ内のリンクは、新しいタブを開かず現在のブラウザタブで開く
- 表示開始日時・終了日時による予約表示は設けず、システム管理者が手動でお知らせのON・OFFを切り替える
- システムで重大な障害を検知した場合でも、システム管理者へのメール通知は送らない

### 5.24 代理店

- 代理店は、クライアントを紹介した外部の協力会社とする
- 代理店は、自社が紹介した会社の申請案件の進捗を確認する
- 代理店（組織）は、代理店マスタで管理する
- 代理店マスタの登録項目は、「代理店コード」「代理店名」「有効／無効」とする
- 代理店マスタは、事務員またはシステム管理者が登録・編集する
- 代理店アカウントは、必ず1つの代理店に紐づける
- 1つの代理店には、複数の代理店アカウントを作成できる
- 会社情報に「紹介代理店」を設定する
- 紹介代理店の設定は任意とし、代理店を経由しない会社には設定しない
- 1つの会社に設定できる紹介代理店は、1つとする
- 紹介代理店は、事務員またはシステム管理者が設定・変更する
- 紹介代理店は、会社情報の必須項目には含めない
- 代理店は、自社が紹介代理店に設定されている会社の申請案件だけを閲覧できる
- 代理店が閲覧できる範囲は、その会社のクライアントが閲覧できる範囲と同じとする
- 代理店は、会社情報、受講者情報、提出書類、契約書、見積もり兼発注書、請求書、講義スケジュールを閲覧できる
- 代理店は、いずれのデータも登録・編集・削除できない
- 代理店は、書類の提出、講義スケジュールの予約、ステータスの変更を行えない
- 代理店は、案件掲示板を閲覧できるが、投稿はできない
- 代理店には、共通通知を送らない
- 紹介代理店を変更した場合は、変更前の代理店から、その会社の申請案件が見えなくなる
- 代理店マスタを無効にした場合は、その代理店に紐づくすべてのアカウントがログインできない
- 会社に設定されている代理店マスタは削除できず、無効化のみとする
- どの会社にも設定されていない代理店マスタは、削除できる
