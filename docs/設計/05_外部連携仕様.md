# 助成金管理システム 外部連携仕様

## 1. この文書について

本システムが連携する外部サービスとの、具体的な手順・パラメータ・エラー処理を定義します。

- 文書状態: 初版
- 作成日: 2026-09-04
- 前提文書: `01_要件定義.md`、`03_技術選定.md`、`04_DB論理設計.md`

## 2. 連携先の一覧

| 連携先 | 用途 | 方向 | 要件 |
| --- | --- | --- | --- |
| freeeサイン（旧 NINJA SIGN） | 契約書の送付・締結・締結済みPDFの取得 | 双方向（本システムから呼び出す） | 5.8 |
| Amazon SES | 見積もり兼発注書・請求書のメール送付 | 送信のみ | 5.9, 5.10 |
| 日本郵便 郵便番号データ | 郵便番号から住所を自動入力 | 取得のみ（月次） | 5.3 |

**いずれも本システムから能動的に呼び出す方式とし、外部からの受信エンドポイントは設けません。**

## 3. freeeサイン（電子契約）

要件5.8の「FREE SIGN」はfreeeサインを指します。API仕様は公開されている OpenAPI 定義
（`https://ninja-sign.com/v1/openapi.yaml`）にもとづきます。

### 3.1 方針

**Webhook は使用せず、ポーリングのみで締結を検知します。**

| 理由 | 内容 |
| --- | --- |
| 環境を分離できない | Webhook の送信先はテナント単位の設定で、freeeサインにサンドボックス環境がありません。検証環境と本番環境で使い分けられず、検証環境の操作が本番へ届く事故が起こり得ます |
| 配信が保証されない | 仕様に「ネットワークエラー等により届かなかったり、複数回届いたりする場合がある」と明記されています。もともとポーリングとの併用が前提でした |

API はクレデンシャルを分けられるため、呼び出す側が制御するポーリングであれば環境を分離できます。
副次的に、公開エンドポイントが1つ減り、署名検証・リプレイ対策・冪等処理が不要になります。

### 3.2 認証

`POST /v1/token` に `client_id` と `client_secret` を送り、アクセストークンを取得します。
利用者のログインを介さないサーバー間連携です。

```
POST /v1/token
{ "client_id": "...", "client_secret": "..." }
→ { "access_token": "...", "expires_in": 3600, "token_type": "Bearer" }
```

以降のリクエストは `Authorization: Bearer <access_token>` を付与します。

- トークンは有効期限まで保持し、期限が切れたら再取得します
- `401` を受け取った場合は、トークンを再取得して**1度だけ**リトライします
- `client_id` / `client_secret` は Secrets Manager で管理し、環境ごとに別の値を設定します

### 3.3 使用するAPI

| 用途 | メソッドとパス |
| --- | --- |
| アクセストークン発行 | `POST /v1/token` |
| テンプレート一覧の取得 | `GET /v1/templates` |
| テンプレートからの文書作成 | `POST /v1/documents` |
| 文書送信 | `POST /v1/documents/{id}/confirmations` |
| 送信ユーザーの取得 | `GET /v1/users` |
| 文書再送信 | `POST /v1/documents/{id}/re_confirmations` |
| 承認依頼キャンセル | `PUT /v1/documents/{id}/signature_requests/cancel` |
| 文書一覧の取得（ポーリング） | `GET /v1/documents` |
| 文書の取得（JSON / PDF） | `GET /v1/documents/{id}` |

### 3.4 文書ステータス

| 値 | 意味 | 本システムでの扱い |
| --- | --- | --- |
| `draft` | 作成中 | 送信前 |
| `in_progress` | 確認待ち | 送信済み・未署名 |
| `awaiting_receipt` | 受け取り待ち | 送信済み・未署名 |
| `approved` | 要確認 | 送信済み・未署名 |
| `concluded` | 完了 | **締結完了。PDF取得の対象** |
| `rejected` | 却下 | 記録のみ。ステータスは自動で進めない |
| `expired` | 有効期限切れ | 記録のみ。ステータスは自動で進めない |
| `trashed` | 削除済み | 記録のみ |

### 3.5 契約書のテンプレートと入力項目

契約書は **freeeサインのテンプレートから生成**します。本システムでPDFを生成したりアップロードしたりはしません。

- テンプレートは事務員が freeeサインの画面で登録・保守します
- **本システムにテンプレートの作成・編集機能は設けません**
- テンプレートIDはシステム設定として保持します

入力項目は、テンプレート設計時に2種類へ振り分けます。

| 区分 | 入力する主体 | 本システムの扱い |
| --- | --- | --- |
| オーナー側の入力項目 | 本システム | 文書作成時に値を渡す。**未指定だと `422` になります** |
| 署名者側の入力項目 | クライアント | 値を渡さない。クライアントが署名時に freeeサイン上で入力する |

**会社名など、契約書の作成時点では確定していない項目は署名者側に配置し、クライアントに入力させます。**

これは業務の順序上の必然です。ステータスは「4 契約書送付済 → 5 契約締結済 → 6 必要事項記入中」の順に
進むため、契約書を送付する時点では会社情報がまだ入力されていません（5.3では事務員が会社名だけを
登録してクライアントを招待する流れです）。

### 3.6 契約書の送付

1. 事務員が本システムで送付操作を実行する
2. `POST /v1/documents` でテンプレートから文書を作成する

```
POST /v1/documents
{
  "template_id": <設定値>,
  "document": {
    "title": "<案件に応じたタイトル>",
    "items": [ { "item_id": <オーナー側必須項目>, "value": "..." } ]
  }
}
```

3. `POST /v1/documents/{id}/confirmations` で送信する

```
POST /v1/documents/{id}/confirmations
{
  "notification_type": "email",
  "sender_id": <設定値>,
  "to": [ { "email": "<会社情報の担当者メールアドレス>" } ]
}
```

4. `contracts` に `freee_sign_document_id` と `sent_at` を記録する

- **`sender_id` はAPIクライアントを利用する場合に必須です。** freeeサイン上の送信ユーザーIDを
  `GET /v1/users` で取得し、システム設定として保持します
- `to` は「文書・テンプレートに設定された相手方の人数分、過不足なく」指定する必要があります。
  相手方が1人のテンプレートを前提とします
- 署名依頼メールは freeeサインから送信されます。本システムからは送信しません（5.8）
- クライアントは本システムにログインせず、署名依頼メールから署名します
- **申請案件のステータスは自動で進めません。** 事務員が手動で操作します（5.1）

**主なエラー**

| コード | 意味 |
| --- | --- |
| `400` | テンプレートが存在しない |
| `401` | 作成者がフォルダへのアクセス権を持たない |
| `403` | フォルダ選択必須設定が有効でフォルダが未選択 |
| `422` | オーナー側の必須入力項目が指定されていない |

### 3.7 再送

`POST /v1/documents/{id}/re_confirmations` を呼びます。同じ契約書に対して行い、送付先は初回と同じ担当者メールアドレスです。

未署名のまま一定期間が経過しても、自動での催促は行いません（5.8）。

### 3.8 送付の取消

`PUT /v1/documents/{id}/signature_requests/cancel` を呼び、`contracts.canceled_at` を記録します。

- 取消しても申請案件のステータスは戻しません（5.8）
- 取消後は内容を修正して改めて送付できます
- 締結済みの契約書は取消も再送もできません

### 3.9 締結の検知（ポーリング）

**実行**: EventBridge Scheduler から ECS の単発タスクを起動します。間隔は**5〜10分**とします。

**対象の抽出**

```sql
SELECT id, freee_sign_document_id
FROM contracts
WHERE sent_at IS NOT NULL
  AND canceled_at IS NULL
  AND pdf_fetched_at IS NULL
```

**問い合わせ**

抽出した `freee_sign_document_id` をまとめて指定し、1リクエストで取得します。

```
GET /v1/documents?ids[]=101&ids[]=102&...&per_page=100
```

- 100件を超える場合はリクエストを分割します
- 未締結の契約書は常時少数のため、通常は1リクエストで完結します
- **前回実行時刻を保持しないステートレスな方式です。** ジョブが落ちても次回に自然と復帰し、
  取りこぼしが構造的に起きません

**反映**

- レスポンスの `status` を `contracts.freee_sign_status` に記録します
- `concluded` の文書は 3.10 のPDF取得へ進みます
- `rejected` / `expired` は記録のみ行い、申請案件のステータスは変更しません

### 3.10 締結済みPDFの取得

単純な1回のダウンロードではありません。2段階の手順が必要です。

1. `GET /v1/documents/{id}` を `Accept: application/json` で呼び、`timestamped` を確認する
2. `timestamped` が `false` の場合は**何もせず終了**する（次回のポーリングで再試行される）
3. `timestamped` が `true` の場合、同じエンドポイントを `Accept: application/pdf` で呼ぶ
4. 取得したPDFをS3へ保存し、`pdf_file_key` / `pdf_fetched_at` / `concluded_at` を更新する

PDFの生成処理中はエラーが返ります（API仕様に明記）。**独自のリトライ機構は実装しません。**
`pdf_fetched_at` が NULL のままなら次回のポーリング対象に残るため、それが再試行として機能します。

### 3.11 手動同期

契約書の画面に「最新状態を取得」ボタンを設けます。

ポーリング間隔ぶんの遅延があるため、事務員が freeeサインの画面で締結を確認した直後に
本システムを開いた場合、まだ反映されていない状況が起こります。このボタンで該当の1件だけを
`GET /v1/documents/{id}` で問い合わせ、その場で更新します。

事務員の操作に対する応答なので同期処理とし、処理中はプログレススピナーを表示します（5.22）。

### 3.12 環境の分離

| 環境 | クレデンシャル | 接続先 |
| --- | --- | --- |
| 本番 | 本番用の `client_id` / `client_secret` | 本番テナント |
| ステージング | 検証用の `client_id` / `client_secret` | **検証用テナント（要確認）** |

freeeサインにはサンドボックス環境がありません。**検証環境と本番環境が同一テナントを共有すると、
検証環境が本番の契約書PDFを取得してしまいます。** 別テナントを用意できるかを確認する必要があります
（7章の確認事項）。用意できない場合は、ステージング環境では連携をモックに切り替えます。

### 3.13 エラー処理

| 状況 | 対応 |
| --- | --- |
| `401`（トークン期限切れ） | トークンを再取得し、1度だけリトライする |
| `429` / `5xx`（ポーリング中） | 即時リトライせず、次回のポーリングに委ねる |
| `429` / `5xx`（事務員の操作中） | 画面にエラーメッセージを表示し、利用者が再実行できるようにする（5.22） |
| PDF生成処理中のエラー | 何もしない。次回のポーリングで再試行される |
| ポーリングジョブ自体の失敗 | CloudWatch アラームから開発チームへ通知する（`03_技術選定.md` 5.7） |

### 3.14 制約

- テンプレートに登録するPDFは**10MB以下**です。テンプレートの登録は freeeサインの画面で行うため
  本システムの実装には影響しませんが、テンプレート作成時に考慮が必要です
- レート制限はAPI仕様に記載がありません。ポーリング間隔の決定に必要なため、確認事項とします

## 4. Amazon SES（メール送信）

### 4.1 送信するメール

| 種類 | 添付 | 送付先 | 要件 |
| --- | --- | --- | --- |
| 見積もり兼発注書 | 自動生成したPDF | 会社情報の担当者メールアドレス | 5.9 |
| 請求書 | 自動生成したPDF | 会社情報の担当者メールアドレス | 5.10 |

- 帳票を生成しただけでは送付しません。事務員が送付操作を実行したときだけ送信します
- **契約書の署名依頼メールは freeeサインから送信されます。本システムからは送信しません**（5.8）
- 仮パスワードはメールまたはLINEで個別に伝える運用のため、システムからは送信しません（5.4）

### 4.2 ドメイン認証

送信元には本システム専用のドメインを使用し、Route 53 に次のレコードを設定します（`03_技術選定.md` 5.8）。

- SPF
- DKIM
- DMARC

これらが未設定または不備がある場合、迷惑メールと判定されるか、そもそも届きません。

### 4.3 サンドボックス解除

**本番運用前に SES のサンドボックス解除申請が必要です。** 解除前は検証済みアドレスにしか
送信できず、クライアント宛の送信テストが行えません。構築の早い段階で申請します。

### 4.4 バウンス・苦情の処理

SNS 経由でバウンスと苦情の通知を受け取り、記録します。
バウンス率が上昇すると SES の送信停止につながるため、CloudWatch アラームで監視します。

### 4.5 エラー処理

送信に失敗した場合は画面にエラーメッセージを表示し、利用者が再実行できるようにします（5.22）。
送信処理の時間は性能目標の対象外です。

## 5. 日本郵便 郵便番号データ

郵便番号から住所を自動入力するために使用します（5.3）。外部APIには依存しません。

- 日本郵便が公開する郵便番号データを取り込み、`postal_codes` テーブルに保持します
- 更新は**月次**とし、EventBridge Scheduler から ECS の単発タスクを起動します
- 更新は洗い替え（全件入れ替え）とし、トランザクション内で実施します
- 更新に失敗した場合は既存データを維持し、CloudWatch アラームから開発チームへ通知します

自前でデータを持つことで、応答時間と可用性を自システムで制御できます。
郵便番号に対応する住所を取得できない場合は、利用者が住所を手入力できます（5.3）。

## 6. 監視

外部連携の失敗は利用者側にエラーが表示されないまま放置されやすいため、次を監視対象とします
（`03_技術選定.md` 5.7）。

| 監視対象 | 検知できない場合に起きること |
| --- | --- |
| freeeサインの締結ポーリングの失敗 | 締結済みPDFが取得されないまま放置される |
| SES の送信失敗・バウンス率 | 見積もり兼発注書・請求書がクライアントに届いていない |
| 郵便番号データ月次更新バッチの失敗 | 住所の自動入力が古いデータのまま動き続ける |

## 7. 確認事項

| # | 項目 | 影響 |
| --- | --- | --- |
| 1 | **検証用テナントの可否** | freee社へ確認。用意できない場合、ステージング環境では連携をモックにします（3.12） |
| 2 | freeeサインAPIのレート制限 | ポーリング間隔の決定に必要です（3.14） |
| 3 | Web API の利用に必要な契約プラン | freee社へ確認 |
| 4 | 「文書承認依頼キャンセル」の意味範囲 | 送信済みの署名依頼の無効化を含むか。要件5.8の「送付を取り消すとFREE SIGN側の署名依頼も無効にする」を満たすかに関わります |
| 5 | 見積もり兼発注書・請求書のメール件名と本文 | 文面を確定する必要があります |
| 6 | freeeサインの送信ユーザー（`sender_id`）とテンプレートID | システム設定として保持する値を確定します（3.6） |
