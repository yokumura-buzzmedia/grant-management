# 助成金管理システム 要件定義書

## 1. この文書について

本書は、助成金管理システムの目的と対象範囲を段階的に合意するための文書です。
一度に詳細を決めず、確認済みの内容から少しずつ追記します。

- 文書状態: 更新中
- 作成日: 2026-08-28
- 今回の確認範囲: システムの目的、アクター、基本業務フロー

## 2. システムの目的（仮）

特定の助成金について、申請に必要な書類の回収、関係者間のやりとり、申請ステータスを一元管理することを目的とします。

想定している効果は次のとおりです。

- 申請に必要な書類と回収状況を把握できる
- 案件ごとの現在のステータスを確認できる
- 関係者が必要なやりとりを行い、次のステータスへ進められる
- 現行システムの複雑さを解消し、安定した業務運用を実現する

## 3. アクター

- クライアント
- システム管理者
- 事務員
- 講師
- 社会保険労務士（社労士）

すべてのアクターが、それぞれのアカウントでシステムにログインします。
申請業務全体は、主に事務員と社労士が進めます。

### 3.1 アクター別の役割

| アクター | 主な役割 |
| --- | --- |
| クライアント | 自社情報と自社の申請案件の閲覧・編集、必要書類の提出、講義スケジュールの予約 |
| 事務員 | 申請業務全体の主担当、すべてのクライアントと申請案件の閲覧・編集 |
| 講師 | 自分が担当する講義スケジュールの確認 |
| 社労士 | すべてのクライアントと申請案件の閲覧、確認、コメントによる事務員のフォロー（案件の編集は不可） |
| システム管理者 | アカウント管理、設定変更、誤操作時のデータ修正 |

## 4. 現行システムの課題

現在は自作のWebアプリを使用していますが、次の課題があるため新システムへリプレイスします。

- 機能が多く、システム全体を把握しきれない
- 不具合が多く、安定した業務運用が難しい

## 5. 基本業務フロー

申請案件は、基本的に次の順序で進めます。

1. 契約書送付
2. 契約締結
3. 書類収集中
4. 書類収集完了
5. 見積/発注送付
6. 発注書回収
7. 請求書送付
8. 入金確認済
9. 研修中
10. 研修完了
11. 助成金受給済
12. 完了

### 5.1 ステータスの変更ルール

- ステータスを主に次へ進めるのは事務員とする
- ステータスは決められた順序で進める
- 原則として、前のステータスには戻せない
- 原則として、途中のステータスを飛ばせない
- 事務員が手動で次のステータスへ進める
- 現時点では、ステータスの自動変更は行わない
- 誤操作時のみ、システム管理者がステータスを修正できる

### 5.2 必要書類の提出・確認フロー

1. すべての申請案件に、共通の必要書類を設定する。
2. クライアントが必要書類を提出する。
3. 事務員が提出書類の内容を確認する。
4. 問題がなければ、事務員が書類を承認する。
5. 不備がある場合は、事務員が不備内容をコメントし、クライアントへ再提出を依頼する。
6. クライアントが修正した書類を再提出する。

書類提出のルールは次のとおりです。

- 必要書類の具体的な名称は要確認とする
- 1種類の必要書類につき、提出できるファイルは1つとする
- 提出できるファイル形式はPDF、JPEG、PNGとする
- 1ファイルあたりの最大容量は50MBとする
- すべての必要書類が承認済みになるまで、事務員はステータスを「書類収集完了」へ進められない
- 承認済みの書類が差し替えられた場合は、承認を取り消し、事務員による再承認を必要とする
- クライアントが書類を提出または再提出したときは、事務員へシステム内で通知する
- 書類の差し替え前のファイルと提出履歴は保存しない

### 5.3 会社情報の登録・編集

クライアントが登録する会社の基本情報は次のとおりです。
すべての項目を必須とします。

| 項目 | 必須 |
| --- | --- |
| 会社名 | はい |
| 法人番号 | はい |
| 代表者名 | はい |
| 業種 | はい |
| 会社形態 | はい |
| 従業員数 | はい |
| 資本金 | はい |
| 郵便番号 | はい |
| 住所 | はい |
| 建物名 | はい |
| 電話番号 | はい |
| 担当者名 | はい |
| 担当者メールアドレス | はい |

- 1社に複数のクライアントアカウントを登録できる
- クライアントは、登録後も自社の会社情報を編集できる
- 担当者名と担当者メールアドレスは、ログインアカウントとは別の会社主担当者情報として管理する
- クライアントが会社情報を変更しても、事務員への通知は送らない

### 5.4 アカウントの作成・ログイン

- クライアントアカウントは、システム管理者または事務員が作成し、クライアントを招待する
- クライアントによる自由な新規アカウント登録は行わない
- 講師と社労士のアカウントは、システム管理者または事務員が作成する
- 事務員アカウントは、システム管理者が作成する
- ログインIDにはメールアドレスを使用しない
- ログインIDは、アカウント作成者が任意の文字列を設定する
- アカウント作成時に、システムが仮パスワードを自動発行する
- 利用者は、自動発行された仮パスワードで初回ログインする
- 初回ログイン後は、利用者自身が新しいパスワードを必ず設定する
- 新しいパスワードを設定するまで、通常のシステム機能は利用できない
- パスワードを忘れた場合、利用者自身によるパスワード再設定は行わない
- システム管理者または事務員が、仮パスワードを再生成する
- 再生成した仮パスワードは、メールまたはLINEで利用者に個別に伝える
- 仮パスワードでログインした場合は、発行理由を問わず、利用者自身による新しいパスワードの設定を必須とする
- 仮パスワードに有効期限は設けない
- 事務員は、事務員、クライアント、講師、社労士のアカウントに対して仮パスワードを再生成できる
- 事務員は、システム管理者の仮パスワードを再生成できない
- 通常パスワードは8文字以上とする
- ログインに多要素認証は使用しない
- ログイン失敗が連続しても、アカウントの自動ロックは行わない

仮パスワードの有効期限、パスワードの最低文字数、多要素認証、アカウントロックは、セキュリティ設計時の再確認事項とします。

### 5.5 講義スケジュールの予約

1. システムは、土曜日、日曜日、祝日を予約不可日とする。
2. 個別に登録された休業日も予約不可日とする。
3. 予約不可日以外を、クライアントが選択できる予約可能日とする。
4. 講義の空き日程は個別に登録しない。
5. 個別の休業日は、事務員またはシステム管理者が登録・変更する。
6. クライアントは、全10時間の講義を2日間、3日間、4日間、5日間のいずれで受講するかを選択する。
7. クライアントは、選択した日数分の講義日と各日の開始時刻を選択し、予約を申請する。
8. システムは、選択した日数ごとの講義時間配分に従い、各日の終了時刻を自動計算する。
9. 2日間で受講する場合は、1日あたり5時間とする。
10. 3日間で受講する場合は、3時間、3時間、4時間の順とする。
11. 4日間で受講する場合は、1日あたり2時間30分とする。
12. 5日間で受講する場合は、1日あたり2時間とする。
13. クライアントは特定の申請案件を選択し、その申請案件に紐づく予約枠を作成する。予約申請時点ではチームを登録しない。
14. 予約枠作成後に、事務員またはシステム管理者がチームを作成する。
15. 1つの予約枠に対して1つのチームを作成し、予約枠とチームを紐づける。
16. チーム作成後に、事務員またはシステム管理者がチームのカリキュラムを登録する。
17. 事務員は予約申請を承認するときに、担当講師を指定する。
18. 事務員の承認と担当講師の指定後に、講義スケジュールを確定する。
19. 1人の講師に、同じ日時の講義を重複して割り当てることはできない。
20. 予約の承認と担当講師の決定時に、クライアントと担当講師へシステム内通知を送る。
21. 同じ日時でも、別の講師を割り当てられる場合は、複数のクライアントの予約を承認できる。
22. 同一日時に確保できる予約枠数の上限は、「講師マスタの有効な講師数 - 1」とする。
23. クライアントが予約を申請した時点で、事務員の承認前でも予約枠を1つ確保する。
24. 講師マスタの有効な講師数が減り、新しい上限を超えた場合でも、すでに受け付けた予約は維持する。
25. 予約申請の承認前は、クライアントが予約日時を変更または予約をキャンセルできる。
26. 予約確定後の日時変更・キャンセルは、事務員またはシステム管理者だけが行える。
27. 予約がキャンセルまたは却下された場合は、確保していた予約枠をすぐに解放する。
28. 予約がキャンセルまたは却下されても、すでに作成されたチームは削除せず保存する。
29. 予約申請を却下する場合は、却下理由のコメントとクライアントへのシステム内通知は行わない。
30. 予約確定後に日時を変更または予約をキャンセルした場合は、クライアントと担当講師へシステム内通知を送る。

### 5.6 申請案件・チーム・カリキュラムの関係

- 1顧客（1社）は、複数の申請案件を持つことができる
- 1つの申請案件は、複数のチームを持つことができる
- 1つの申請案件は、複数の予約枠を持つことができる
- 1チームに登録できるカリキュラムは1つとする
- 1つのカリキュラムに対して、複数の講義日を予約できる
- チームは、事務員またはシステム管理者が作成する
- チームは、クライアントによる講義予約の後に作成する
- 予約申請時点では、仮のチームやチーム予定データは登録せず、予約枠だけを作成する
- 1つの予約枠から1つのチームを作成し、予約枠とチームを紐づける
- 予約がキャンセルまたは却下された後に残したチームは、新しい予約枠に紐づけて再利用できる
- チームの基本情報として、チーム名と受講者を登録する
- 受講者情報の初回登録は、クライアントが行う
- 初回登録後の受講者情報は、クライアント、事務員、システム管理者が編集・削除できる
- 受講者の具体的な登録項目はTODOとし、後で確定する
- 1チームあたりの受講者数に、最小・最大人数の制限は設けない
- 受講者は顧客（会社）に紐づけて管理する
- 一度登録した受講者は、同じ顧客の別の申請案件で再利用できる
- 同じ申請案件内では、1人の受講者を複数のチームに重複して登録できない
- 受講者がチームに登録済みの場合でも、受講者情報自体を削除できる
- 受講者を削除した場合は、所属しているチームからも自動で削除する
- 受講者を削除した場合は、研修完了後の過去記録にも受講者の名前を残さない

### 5.7 カリキュラム管理

- カリキュラムは、事務員またはシステム管理者が登録・編集する
- クライアントはカリキュラムを登録・選択しない
- 事務員またはシステム管理者が、クライアントによる講義日時の予約後に、カリキュラムをチームに登録する
- カリキュラムの具体的な登録項目はTODOとし、後で確定する
- カリキュラムの登録前は、クライアントが受講日数、各講義日、各日の開始時刻を選択する
- すべてのカリキュラムの講義時間は、合計10時間で固定とする

### 5.8 契約書送付・契約締結

- 契約書の作成には、外部の電子契約サービス「FREE SIGN」を使用する
- 契約締結は、FREE SIGN上で行う
- クライアントへの契約書の送付方法は要検討とする
- 本システムとFREE SIGNは自動連携する
- FREE SIGNで締結済みとなった契約書のPDFを、本システムに保存する
- FREE SIGNで契約締結を確認した後、事務員が本システムのステータスを手動で「契約締結」へ進める
- 事務員が本システムで契約書の送付操作を実行したときに、FREE SIGNへ契約書の作成・送付を連携する
- FREE SIGNで契約締結が完了したら、本システムが締結済みPDFを自動取得して保存する
- 1つの申請案件に登録する契約書は1つとする
- FREE SIGNとの自動連携方法と利用可能なAPIは、技術設計時の確認事項とする

### 5.9 見積もり兼発注書の送付・回収

- 見積書と発注書は別ファイルとせず、1つの「見積もり兼発注書」とする
- 見積もり兼発注書は、本システムが登録データから自動生成する
- 見積もり兼発注書を生成しただけでは、クライアントへ送付しない
- 事務員が本システムで送付操作を実行したときだけ、見積もり兼発注書をクライアントへ送付する
- 見積もり兼発注書は、メールでクライアントへ送付する
- 見積もり兼発注書の送付先は、会社情報の「担当者メールアドレス」とする
- 署名・押印済みの見積もり兼発注書の回収方法は要検討とする
- 1つの申請案件に登録する見積もり兼発注書は1つとする

### 5.10 請求書送付・入金確認

- 請求書は、本システムが登録データから自動生成する
- 請求書を生成しただけでは、クライアントへ送付しない
- 事務員が本システムで送付操作を実行したときだけ、請求書をクライアントへ送付する
- 請求書の送付先は、会社情報の「担当者メールアドレス」とする
- 入金を確認した後、事務員が申請案件のステータスを手動で「入金確認済」へ進める

### 5.11 研修開始から完了まで

- 申請案件のステータスは、事務員が手動で「研修中」へ進める
- 申請案件のステータスは、事務員が手動で「研修完了」へ進める
- 助成金の受給は事務員が確認する
- 助成金の受給確認後、事務員が申請案件のステータスを手動で「助成金受給済」へ進める
- 「助成金受給済」の後、事務員が申請案件のステータスを手動で「完了」へ進める
- 各講義日の「実施済み」「中止」などの実施結果は、本システムに記録しない
- 受講者ごとの出欠を本システムに記録するかは、TODOとして後で検討する

### 5.12 案件掲示板

- 申請案件ごとに、案件全体についてやり取りする掲示板を設ける
- 提出書類ごとに個別のコメント欄は設けない
- その申請案件を閲覧できるすべてのアクターが、掲示板を閲覧し投稿できる
- 掲示板の新しい投稿には、共通のシステム内通知機能を使用しない
- 掲示板に未読の投稿がある場合は、案件画面の掲示板タブに未読バッジを表示する
- 自分以外の利用者による新しい投稿だけを、未読バッジの対象とする
- 利用者が掲示板タブを開いた時点で、その掲示板の投稿を既読にして未読バッジを消す
- 投稿者は、自分の投稿を編集・削除できる
- 掲示板の投稿には、ファイルを添付できる
- 添付できるファイル形式は、PDF、JPEG、PNGとする
- 添付ファイルの最大容量は、1ファイルあたり50MBとする

### 5.13 共通通知

- 書類提出や予約確定などの通知は、画面上部のベルアイコンから一覧表示する
- ベルアイコンには、未読通知の件数をバッジで表示する
- 利用者が通知を選択した場合は、通知内容に対応する申請案件または予約画面へ移動する
- 利用者が通知を選択した時点で、その通知を既読にする
- 通知一覧に「すべて既読にする」操作を設ける
- 過去の通知は自動削除せず、すべて保存する
- 案件掲示板の新しい投稿は、共通通知の対象に含めない

### 5.14 ダッシュボード・案件一覧

- 事務員、システム管理者、社労士には、ログイン後の最初の画面としてダッシュボードを表示する
- 事務員とシステム管理者のダッシュボードには、ステータスごとの案件数を表示する
- 社労士のダッシュボードには、事務員と同じステータスごとの案件数を閲覧専用で表示する
- クライアントには、ダッシュボードを設けない
- クライアントは、ログイン後の最初の画面として自社の申請案件一覧を表示する
- 講師には、ダッシュボードを設けない
- 講師は、ログイン後の最初の画面として自分が担当する講義スケジュールを表示する
- ダッシュボードのステータス別案件数を選択すると、選択したステータスで絞り込んだ案件一覧へ移動する
- 案件一覧では、会社名による検索を行える
- 案件一覧では、申請案件のステータスによる絞り込みを行える

### 5.15 申請案件の作成・削除

- 申請案件は、事務員またはシステム管理者が作成する
- 申請案件の作成時に、システムが案件番号を自動発行する
- 申請案件は、事務員またはシステム管理者が削除できる
- クライアント、講師、社労士は、申請案件を作成・削除できない
- 申請案件を削除する場合は、データを残さず完全に削除する
- 削除した申請案件は復元できない
- 申請案件は、現在のステータスに関係なく削除できる
- 進行中または完了済みの申請案件も削除できる
- 完全削除を実行する前に、確認ダイアログを表示する
- 申請案件を削除した場合は、その案件専用の書類、予約、チーム、掲示板投稿などの関連データもすべて削除する
- 申請案件を削除しても、「削除した利用者」「削除日時」「案件番号」の削除履歴は保存する

## 6. 次に確認したいこと

1. 案件を削除しても、会社情報とクライアントアカウントは残しますか。
2. 会社に紐づく受講者情報は、削除した案件以外でも再利用できるため残しますか。
3. 削除履歴は、事務員とシステム管理者の両方が閲覧できるようにしますか。

## 7. 次回の追記予定

上記3点の回答を反映し、案件削除時に残す共通データと削除履歴の閲覧権限を整理します。
